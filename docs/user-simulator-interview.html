02 · RL Formulation

User Simulator 不是陪聊模型，而是环境转移核

在多轮工具 Agent 中，Policy 产生 Agent action 或自然语言 \(a_t\)，用户模拟器根据任务 instruction \(I\)、对话历史 \(h_t\) 和最新 Agent 文本生成下一轮用户行为：

\[ u_{t+1} \sim U_{\phi}\!\left(u \mid I, h_t, a_t\right). \]

因此完整环境动力学不是只由数据库和工具决定，而可以写成：

\[ P_{\phi}(s_{t+1},u_{t+1}\mid s_t,h_t,a_t) = P_{\text{env}}(s_{t+1}\mid s_t,a_t)\, U_{\phi}(u_{t+1}\mid I,h_t,a_t). \]

固定 User Simulator 参数 \(\phi\) 时，主 Policy 的优化目标实际是 \(J(\theta;\phi)\)。如果训练过程中随意改变 Simulator、Prompt、温度或 STOP 规则， 就不再是在同一个 MDP 上比较算法：

\[ J(\theta;\phi) = \mathbb{E}_{\tau\sim p_{\theta,\phi}(\tau)} \left[\sum_{t=0}^{T}\gamma^t r_t\right]. \]

STOP 是 termination hazard

它不是一句普通礼貌话，而是决定 episode 是否在当前历史结束的控制 action：

\[ \lambda_{\phi}(h_t) = P_{\phi}(u_{t+1}=\texttt{STOP}\mid I,h_t,a_t). \]

premature STOP 截断可完成轨迹；delayed STOP 延迟 verifier、增加无意义 horizon，并可能把成功 tail 拖成 malformed。

它会污染 GRPO 相对优势

同一 task 的组内 reward 差异同时来自 Policy 采样和 User 分支：

\[ \operatorname{Var}(R) = \mathbb{E}_{a}\!\left[\operatorname{Var}_{u}(R\mid a)\right] + \operatorname{Var}_{a}\!\left(\mathbb{E}_{u}[R\mid a]\right). \]

若某条 rollout 因 User 偶然泄漏 ID 而高分，group-relative advantage 会错误奖励 Policy。

面试核心判断 好的 User Simulator 不是“更配合”，而是让目标、可观测性、信息披露、fallback 和终止边界与真实业务一致， 从而提供稳定但不失真的 occupancy distribution。

04 · Pilot Audit

为什么先做 16 类危险边界，而不是直接全量生成

Pilot 不是随机抽样，而是 adversarial boundary suite：覆盖 progressive disclosure、unknown ID、 write confirmation、compound goal、fallback、missing user-facing output、temporal trigger、malformed recovery 与 persistent persona。每类采样 3 次，用来验证决策稳定性而不是自然频率。

Thinking 关闭不是经验主义，而是失败归因

high thinking、1,600 output token 时，成功样本 completion P90 为 1,408、最大 1,574， 最终出现 12 个空 content 和 6 个截断 JSON。提高到 4,096 证明主要问题是 reasoning 挤占输出， 不是边界判断能力不足；但本任务只需要可审计分类与一句短回复，继续保留长 reasoning 没有收益证据。

低温不等于模板坍缩

temperature 从 0.8 降到 0.3，是为了固定事实和终止语义。多样性主要来自不同 state、persona、 active goal 与历史，而不是让同一决策边界高温漂移。STOP、本人口述 ID 和明确 confirmation 本来就应该稳定。

Pilot 的反向价值 task 34 的人工 complete case 曾漏掉第三条 upcoming reservation，却写了三条票价的总额 1,016 美元。 Teacher 持续追问反而是正确的；回查数据库后补齐 A90KR2 = 308，说明 Pilot 同时在测模型、标签与 evaluator。

06 · Grounding Forensics

0 privileged leak 为什么仍然不够

v1.5 做对了信息流控制：gold actions、tool results、reward 和 hidden IDs 都不进入 Teacher 请求。 这能阻止复制隐藏答案，但不能阻止 Teacher 自己创造一个新 ID，也不能阻止它把可见字符串换一种实体类型使用。

真实盲区 OMAR1234、A1B2C3、RES12345 并不在 privileged block， 所以旧 leak detector 不会报警；但它们同样是错误的世界状态。
第二轮发现 Occurrence 为什么普通字符串检查不够
unsupported reservation ID 24 模型自造实体，不一定命中 privileged list
Agent example copied as reservation 11 ABC123 可见，但只是格式示例，不是用户事实
placeholder identifier 21 ...、[ID]、[date] 会污染真实回复风格
user ID mislabeled as reservation ID 7 字符串来源可见，但实体类型错误
unsupported airport / city 14 instruction 只写 JFK 或 Texas，不能补出 LAX、Chicago、Dallas
unsupported DOB year 3 输入没给 DOB，不能用常识补全
flight/payment/other typed issue 6 需要按 flight、payment、user、reservation 分类型校验

最终可审计 raw population 共 69 个 target 受影响、86 个 issue occurrence。当前 validator 采用 “observable source + entity type + exemplar semantics + route alias” 四层检查；Prompt v1.6 同时明确 Agent example 不是事实，缺 reservation ID 或 DOB 时必须诚实表达未知。

审计原则 不能把人工修订伪装成纯 Teacher 结果。最终每条样本都有 target_provenance、audit version 与 semantic action，支持回溯和消融。

07 · Training Contract

Student 学的是“下一句用户行为”，不是 Teacher 的审计 JSON

Teacher 富标签

{
  "decision": "continue",
  "is_over": false,
  "termination_reason": "continue",
  "goal_status": "in_progress",
  "communication_status": "partial",
  "response": "Please give me the exact total.",
  "resolved_goals": ["both cancellations"],
  "unresolved_goals": ["exact total cost"],
  "evidence": [{"turn_index": 6, "fact": "..."}]
}

结构字段只用于 QA、归因、quarantine 与统计。

Student 纯文本 target

{"role": "assistant",
 "content": "Please give me the exact total."}

终止时唯一合法 target：

{"role": "assistant",
 "content": "###STOP###"}

因此不需要修改现有 runtime parser。

只监督新生成的最后一个 assistant turn：

\[ \mathcal{L}_{\text{SFT}} = -\sum_{i\in \mathcal{M}_{\text{last-assistant}}} \log p_{\phi}(y_i\mid y_{<i}, I, h_t, a_t). \]

历史 Customer turn 没经过当前 Teacher 逐轮复核，若使用 all-assistant loss， 就会把旧 Simulator 的 delayed STOP、错误坚持和信息泄漏一起蒸馏进去。

08 · Case Studies

同一个 STOP/CONTINUE 标签下，业务语义可能完全不同

Premature STOP · task 4

前三项完成，不代表 gift-card payment 已完成

Scenario 同时要求 cabin、baggage、passenger、payment。Agent 只确认前三项并问是否还需要帮助。

错误：###STOP###

正确：“Yes, I'd like to use my gift card for the payment.”

否则主 Policy 会学到部分 DB 动作完成即可终止。

Delayed STOP · task 9

Agent 已明确给出 Mastercard 总额

最新文本包含 “Total amount charged to your Mastercard: $2,033”。

错误：再次询问已经给出的总额。

正确：###STOP###

但相邻状态若没有 2,033 美元，仍必须 CONTINUE；不能按 task 粗标。

Grounding · Agent exemplar

ABC123 是格式示例，不是 reservation

Agent 说“reservation ID looks like ABC123”只是教用户识别格式。

错误：“My reservation is ABC123.”

正确：说明当前不记得 ID，请求按账户或姓名查找。

这是 observable 字符串，但不是 observable fact。

Same-decision error · task 11

CONTINUE 正确，金额阈值逻辑仍可写反

fallback 条件要求证书金额超过 100 美元时改用其他支付方式。

错误：把 125 美元解释成低于 100 美元。

正确：承认超过阈值并触发指定 fallback。

decision-match 指标无法发现这种业务错误。

Ranking semantics · task 25

second-cheapest 不是 cheapest

候选组合中，HAT069 + HAT258 总价 290 美元是目标 second-cheapest；错误 target 却选择 HAT023 的最低价。

两者都可能是 CONTINUE，但会把错误偏好写进训练环境。

Communication gap · task 34

DB 已完成，但精确总价未向用户可读地告知

若 Agent 输出 malformed total，persistent 用户继续要求一个明确数字是正确行为。

完整事实是 402 + 306 + 308 = 1,016 美元；只有三条 upcoming reservation 和总额全部告知后才 STOP。

这条样本教会模型什么

  1. 识别 basic-economy 条件后激活升级 fallback；
  2. 保留两笔取消目标，不能因升舱完成就 STOP；
  3. 只使用 Agent 已提供的卡尾号，不虚构 payment ID；
  4. 到达时序边界后才激活“其他 upcoming flights + 总价”；
  5. 把取消原因和新查询合并为一条简洁、自然的下一轮回复。

它没有证明：Student 下一轮还能稳定记住这些目标；这必须由 Student-prefix rollout 验证。

为什么 STOP 不等于 success？

最终 193 个 STOP 中，175 个是 goal_satisfied，8 个是 cannot_continue，10 个是 goal_failed。用户在无法继续或 fallback 全部失败时也需要结束对话，但 terminal verifier 仍可给 0。

为什么不能把所有长循环都标 STOP？

长度只是症状。task 34 在 Agent 连续返回乱码总价时继续追问，体现了 persistent persona 和未决 communication goal。强行 STOP 会让 Policy 学会 malformed final answer 也能结束。

09 · Residual Risk

单步对齐通过后，最大的剩余风险是 Student 自生成 history

当前 SFT 样本在历史 prefix 上学习下一轮用户回复。部署时，第 \(t+1\) 轮看到的历史包含 Student 自己在第 \(t\) 轮的输出，因此训练状态分布与上线 occupancy 不完全相同：

\[ \mathcal{D}_{\text{SFT}}(h_t) \neq d^{\pi_{\text{agent}},U_{\phi}}(h_t). \]
1,148 能够链接到下一历史状态的自然样本
46 Teacher target 能逐字重建下一历史 prefix

必须补的 Student-prefix 验收

  1. 固定 Agent script：控制 Agent 信息披露顺序，让 Student 连续响应多轮。
  2. 事实 ledger：追踪 reservation、user/payment ID、DOB、航班、金额和已完成目标。
  3. 跨轮约束：已披露信息不能漂移，未知信息不能突然变已知，完成目标不能反复索要。
  4. termination trace：分别统计 premature STOP、delayed STOP、courtesy tail 与 max-turn。
  5. 分支恢复：Agent 给出错误、澄清或 fallback 时，User persona 和偏好仍应保持。
为什么暂时不做 history summary 当前样本最多 27 条 message，保守序列上界 13,548，低于 max length 16,384；核心难点不是塞不下， 而是总结器可能丢失 reservation、金额、fallback 条件和“已告知/未告知”状态。先验证无 summary 的多轮一致性； 只有真实 rollout 出现长度瓶颈，再引入结构化、可校验的 state summary，而不是自由文本压缩。

10 · Evaluation

离线指标只是门禁，在线交叉实验才决定是否放行

Termination 不能只看 accuracy

\[ \text{STOP Precision} = \frac{\mathrm{TP}_{\text{stop}}} {\mathrm{TP}_{\text{stop}}+\mathrm{FP}_{\text{stop}}}, \qquad \text{STOP Recall} = \frac{\mathrm{TP}_{\text{stop}}} {\mathrm{TP}_{\text{stop}}+\mathrm{FN}_{\text{stop}}}. \]

第一阶段优先 precision，因为 premature STOP 会永久截断可完成轨迹并改变状态访问分布； recall 稍低主要增加成本，之后再用 complete-boundary 样本降低 late-STOP latency。

11 · Interview Narrative

面试时怎样把这项工作讲出算法与工程深度

30 秒版本

User Simulator 不是陪 Agent 聊天的辅助模型，而是多轮 RL 的 observation generator 和 termination policy。 它会改变 episode 长度、occupancy distribution、reward 结算时机和 GRPO 的组内方差。我先区分 DB 完成与用户可见完成， 再用 16 类 adversarial boundary case 校准 STOP/CONTINUE；full batch 后又通过 typed grounding 发现旧 leak gate 看不到的 自造 ID、Agent exemplar copying、实体类型混淆与 route/city 幻觉。最终 1,463 条数据实现单步 runtime 对齐，但我仍把 Student-prefix rollout 和 cross-simulator A/B 作为放行条件，没有把静态审计包装成在线收益。

三分钟项目闭环

  1. 现象：业务完成后 User 不 STOP，或 Agent/User 在工具阶段后循环。
  2. 拆因：delayed STOP、Agent communication gap、malformed answer、fallback、verifier gap 不能混为一类。
  3. 环境穿刺：User 不看 tool result，只有 exact STOP 才触发 terminal verifier。
  4. 数据审计：80 条主 Agent 成功 SFT 没有 STOP；400 条历史中 STOP 与 reward 不等价。
  5. Teacher 管线：observable-only DeepSeek 富标签，Student 只学自然回复；privileged 信息只供本地 QA。
  6. Pilot：从 thinking 截断、高温漂移、人工 case 错误迭代到 48/48。
  7. Full 穿刺：发现 69 个 grounding-affected target、57 条同 decision 语义重写、50 个污染下游 prefix。
  8. 边界：1,463 条离线可训练；LoRA、多轮 Student-prefix 和主 Agent 收益待实验。
追问：这不就是调 Prompt 吗？

Prompt 只是把环境假设表达给 Teacher。算法含量在于：区分 \(z_t^{env}\) 与 \(z_t^{comm}\)， 把 STOP 建模为 termination hazard，明确 Simulator 对 occupancy 和 advantage variance 的影响， 并把信息权限、role flip、loss mask、事实接地、prefix contamination、holdout 隔离和 cross-play 变成可执行合同。

追问：为什么不直接用规则在 verifier success 时 STOP？

verifier success 与用户可见完成不是同一事件。DB 成功但 total savings 没说，用户仍应继续； Agent 声称成功但 DB 失败，User 可能停止、verifier 仍应给 0。把 verifier-ready 注入 User observation 会泄漏真值并改变 benchmark。

追问：为什么不直接用更强模型在线当 User？

强模型适合作为 Teacher 和 cross-eval 上限，但在线 RL 调用量大，成本、延迟、版本漂移和供应稳定性会让环境非平稳。 微调固定 Qwen3-14B 便于控制 MDP；强 Simulator 保留为外部评估，防止 co-adaptation。

追问：怎样证明微调后的 User 真的有价值？

先做 Student-prefix consistency；再固定 Policy 只替换 User，隔离环境效果；随后固定 User 分别训练 Policy， 做 train-simulator × eval-simulator 交叉矩阵。只有 unseen task 和异构 Simulator 上仍提升，才是 Agent 能力提升。

追问：为什么当前不做 history summary？

当前最大保守序列上界 13,548，小于 16,384，长度并非已证实瓶颈。自由文本 summary 反而可能丢失金额、 reservation、fallback 和 communication-completeness。先在完整历史上验证微调模型；若真实 rollout 出现截断， 再引入 schema 化 state summary，并用原 history 做事实等价校验。
