Bidirectional audit · Scheme 2 · 2026-07-30

UserRL × τ-bench：方案二应当怎样落地

先说结论：UserRL 适合当前航空订票任务的“动态用户 + 规则环境”范式，但当前 user-simulator-judge 分支不是 UserRL 原算法复现。它是 LLM-as-Judge 扩展，必须把终局规则奖励与 Judge 辅助信号彻底解耦。

论文—源码—数据双向对齐 官方源码已公开 当前分支：codex/user-simulator-judge 只做静态/逻辑检查，未启动训练或模型
阅读原论文 查看官方代码 查看当前 Judge 实现
01 · 论文事实

User simulator 不是 Judge

UserRL 中 LLM 负责生成动态用户回复；有限状态 Gym 的规则转移负责增量奖励与终局任务完成，二者职责不同。

02 · 当前代码

这是一个相关但独立的扩展

同一 Qwen3-14B 同时扮演用户和 Judge，评价一次用户回复前的整个交互段；信号相关、有偏，不能替代 verifier。

03 · 已修语义

Outcome 纯净，Judge 有界且可关闭

session score 只保留 τ-bench 0/1 outcome；Judge 以 0.5 为中性点映射到 [-1,1]，失败不补值、不改权重。

04 · 建议默认

先诊断，后小权重训练

默认仅记录 Judge 分数、有效率与跨轨迹 outcome 相关性；通过 held-out 校准后，才打开至多 0.05 的辅助贡献。

阅读路径：先拆清 UserRL 与 LLM Judge 的边界 → 对照论文公式和官方源码 → 看旧分支为何会重复计奖 → 用 task 0 真实订票 case 解剖每个信号 → 最后决定何时可进入训练消融。

01 · Concept boundary

先纠正最容易混淆的一点：UserRL ≠ 用户模拟器打分

UserRL 的设计是“双系统”：LLM user simulator 负责自然、动态的用户语言；Gym 作为有限状态机，以确定性规则更新状态并产生增量奖励，最终任务完成仍由规则判定。当前分支则新增第二次 LLM 调用，让用户模型兼任 Judge。这可以是工程实验，但不能借用 UserRL 名义把主观分数写成规则真值。

可继承：环境范式

动态用户、规则 verifier、分组 rollout、轨迹级排序，这些都很适合当前航空订票。

不可直接套：dense $r_t$

当前 τ-bench 主要提供终局 0/1，工具调用通常没有可靠的“进展增量奖励”；UserRL 的 mapper 缺少同语义输入。

可实验：Judge auxiliary

Judge 可以补充沟通/过程诊断，但只能是可关闭、可校准、有界的弱信号，不能覆盖 DB、政策与最终状态。

方案二是否适合当前数据集？适合作为“用户交互能力 + 辅助过程诊断”方案；不适合把同一个 simulator 的主观判断直接当成新的 terminal reward。若要复现 UserRL 原算法，应先给 τ-bench 构造规则化、可验证的增量事件奖励，再接 grpo_multiturn，而不是用 Judge 分数冒充 $r_t$。

02 · Paper and official source

UserRL 原算法：同一份规则增量奖励，两条独立的重映射路径

Figure 1 最关键的分界线位于 Reward Calculator：Gym 先产生原始逐 Turn 奖励 $r_t$；计算器再分别生成 trajectory score 与 turn credit。模拟用户只影响交互内容，不拥有终局 verifier 的裁决权。

源码状态（核验日期：2026-07-30）：官方仓库已公开，并提供 algorithm.adv_estimator=grpo_multiturn、Equalized/R2G/EM turn mapping 与 Sum/R2G trajectory scoring。当前项目分支没有移植该 estimator，因此只能称为“受 UserRL 启发的 Judge 辅助 GRPO”。

Action与模拟用户直接沟通；Gym 返回动态用户回复。
Search检索外部知识或候选项；后端返回结构化或文本结果。
Answer提交候选解；目标可验证时由 Gym 检查正确性或完成状态。

论文公式与官方 core_algos.py 的两个不一致 报告和实验必须显式选择语义，不能把“官方源码”自动等同于“论文公式”。
  1. Trajectory Sum：论文式 (5) 是 $\sum_t r_t$；官方源码 compute_turn_credits() 的 “Sum” 实际计算 sum(turn_rewards) / len(turn_rewards)，是均值。对变长轨迹，两者排序不同。
  2. 标准差：论文给出总体标准差（除以 $n$）；官方源码使用 PyTorch 默认 torch.std，通常是样本标准差修正。小 group 下数值会不同。
  3. Turn advantage 组合：论文式 (7) 直接写成 $(\tilde r_t-\mu_Q)/(\sigma_Q+\eta)$；官方源码先把 turn credits 填到 token，再用组归一化 trajectory score 计算一个整轨迹 scaling factor，使 turn-credit 总量匹配 trajectory advantage。除特殊情形外，两者不是同一个数值算法。

因此若后续移植原算法，建议先将“paper-exact”与“official-source-compatible”做成两个明确模式，并用固定数例锁定，而不是静默选一个。

03 · Reward design

两层奖励必须分开：本轮怎么分，整条怎么排

UserRL 最实用的贡献，是把 Turn-Level Reward Shaping 与 Trajectory-Level Scoring 变成两个独立旋钮。前者决定同一轨迹里各 Turn 的训练信号，后者决定同一任务下不同轨迹如何比较。

第一层：把原始 Turn 奖励映射给本轮 token

$$R(x_{t,k})=\tilde r_t,\qquad k=1,\ldots,L_t$$

怎么读：第 $t$ 个 Turn 内所有策略 token 共用 $\tilde r_t$；不同 Turn 可以不同。$\tilde r_t$ 不是固定定义，而是可选择的奖励映射。

Equalized

每个 Turn 给常量 $c$。强调所有交互的结构性价值，但完全不区分贡献。

Reward-to-Go

$\tilde r_t=\sum_{j=t}^{T}\gamma^{j-t}r_j$。把未来收益传回早期动作，鼓励铺垫性 Turn。

Exponential Mapping

把 $[0,1]$ 非线性映射到 $[0.5,1]$，避免小的正向进展被淹没。

第二层：把整条轨迹压成 GRPO 的标量

$$R_{\mathrm{traj}}^{\mathrm{sum}}(\tau)=\sum_{t=1}^{T}r_t,\qquad R_{\mathrm{traj}}^{\mathrm{r2g}}(\tau)=\sum_{t=1}^{T}\gamma^{t-1}r_t$$

怎么读：Sum 只关心累计进展；Trajectory R2G 让更早取得进展的轨迹得分更高，因此把“少绕路”编码进组内排序。

最后：用轨迹统计量标准化每个 Turn

$$A(x_{t,k}\mid Q)= \frac{\tilde r_t^{(i)}-\mu_Q}{\sigma_Q+\eta}$$

怎么读：分子是本轨迹第 $t$ 个 Turn 的映射奖励，基准却来自同一任务各轨迹的 trajectory score 均值与方差；这正是 UserRL 把“局部信号”和“全局排序”结合的位置。

论文自己的反思：简单 heuristic 并不能真正识别 Turn 的因果贡献。EM 会把所有零奖励 Turn 映射成同样的中间值；R2G 依赖 reward 的时序与质量。论文实验更支持“trajectory scoring 比细粒度 turn differentiation 更关键”。这正是当前分支不应让未经校准的 Judge 同时进入 session 与 turn 两条链路的原因。

当前安全语义的核心代码 以下片段对应分支中的真实实现，不是伪代码。 
@dataclass(frozen=True)
class JudgeSignalPolicy:
    neutral_score: float = 0.5

    def compute(self, feedback: JudgeFeedback) -> Optional[float]:
        if not feedback.valid:
            return None  # 无事件，不补 0，不改变分母
        score = max(0.0, min(1.0, feedback.score))
        if score >= self.neutral_score:
            return (score - self.neutral_score) / (1 - self.neutral_score)
        return (score - self.neutral_score) / self.neutral_score

# session 主目标始终来自规则环境
return {
    "score": outcome,
    "outcome_score": outcome,
    "judge_mean_score": mean(valid_scores) if valid_scores else None,
}

路径：src/envs/reward_fusion.py 与 src/envs/tau_bench_interaction.py。Judge score=0.825、neutral=0.5 时，辅助信号为 0.65；最终注入权重若为 0.05，整轨迹平均贡献最多 0.05。

05 · Real dataset case

用当前数据集 task 0 解剖一次完整训练样本

案例直接来自当前分支 tau-bench/tau_bench/envs/airline/tasks_test.py 的第一个任务：用户 Mia 从纽约飞西雅图，5 月 20 日单程、11 点后、经济舱、低价优先、三件行李、不买保险，并有证书与信用卡支付约束。目标动作是一次参数完整的 book_reservation。

隐藏任务约束

  • 用户只回答被问到的信息，不主动泄露全部 slot。
  • JFK → SEA、2024-05-20、economy、低价优先。
  • 3 件行李、insurance=no。
  • 证书优先；受单证书限制时选更大证书，再用 7447 卡补差。
  • 生日应从 user profile 获取，不应反复询问。

规则终局目标

Verifier 检查最终数据库状态是否等价于 gold book_reservation：正确用户、航班 HAT136/HAT039、Mia Li 的 DOB、三件行李、支付拆分和 no insurance。只有这个结果决定 outcome=1。

06 · Implementation alignment

当前代码实现了什么，没有实现什么

审核后的分支是一条“outcome-only GRPO + 可选 interaction-cycle Judge auxiliary”链路。它解决的是稀疏奖励下的过程诊断，不是完整 UserRL estimator。报告、配置名和实验结论都必须保持这一边界。

这里的辅助信号最终会先在 compute_grpo_outcome_advantage() 中按序列求和，变成一个 trajectory scalar，再组内归一化并广播给所有 response token。interaction-cycle span 只保留可观测性，不形成局部梯度；它没有实现论文式逐 Turn advantage，也不应标成 grpo_multiturn。

静态测试锁定的关键不变量 本轮按用户要求未执行测试；这些测试用于后续可运行验证。
  • Judge fenced JSON 能解析，越界维度被 clamp，非数值响应显式 unavailable。
  • Judge prompt 包含真实工具 observation / error，而不是只有 is_error 布尔值。
  • raw Judge=0.825 映射为 centered signal=0.65；invalid Judge 返回 None。
  • 开启 Judge 时，session score 仍严格等于 outcome；失败轨迹不会因高 Judge 获得正 terminal score。
  • trainer 拒绝 [-1,1] 之外的 active signal，拒绝大于 0.1 的 turn weight。
  • Judge/outcome 相关性在跨轨迹 batch 上计算，不在单轨迹稀疏事件上计算。

若要继续走 paper-faithful UserRL，正确顺序是什么

  1. 从 τ-bench gold actions、DB state diff、policy checks 中定义规则化增量事件，例如首次获得必要实体、候选集合满足约束、正确 write state transition；不要从终局 outcome 反推。
  2. 在固定离线轨迹上验证 $r_t$ 的单调性、不可重复刷分、错误回滚与成功路径覆盖。
  3. 分别实现并测试 paper-exact 与 official-source-compatible 的 Sum、R2G、std 语义。
  4. 再接 grpo_multiturn，先做 Equalized/R2G 与 outcome-only GRPO 对照；Judge 保持诊断，不与规则 $r_t$ 同时混合。

07 · Decision and ablation

最终判断：方案可做，但结论必须拆成两条实验线

A 线：当前可进入校准

Outcome-only GRPO 保持主目标；Judge 仅记录 interaction-cycle 诊断。先看有效率、成功/失败分布、冲突样本和不同 simulator 的稳定性。

B 线：真正 UserRL 适配

另行构建规则化 dense $r_t$ 与 grpo_multiturn；不能把 Judge score 直接改名为 UserRL turn reward，也不能与 A 线同时改多个变量。

当前置信度

代码语义已从“不可解释的多源融合”修到“可解释、默认无侵入”。但没有训练数据证明 Judge auxiliary 会提升 unseen success，因此现阶段只能判为可消融，不能判为有效。

最小、可归因的实验矩阵

  1. Baseline：当前 outcome-only GRPO，Judge 采集关闭或仅日志；锁定模型、rollout、seed、simulator 与 verifier。
  2. Diagnostic-only：Judge 开启、training gate 关闭。校准指标至少包含 valid rate、成功/失败均值差、outcome correlation、冲突 top cases、tool-error 条件分布。
  3. Aux-0.02 / Aux-0.05：只有 Diagnostic-only 通过门槛后，开启两个小权重；不建议先试 0.1。
  4. Independent Judge：同模型 Judge vs 独立模型/规则 Judge，检验“同源偏差”是否造成虚假收益。
  5. User style split：reactive、情绪化、反悔/替代方案、政策冲突任务分别统计，而不是只看总体 success。
  6. UserRL track：规则 dense $r_t$ + Equalized/R2G；单独实验名、单独报告，不与 LLM Judge auxiliary 混称。
