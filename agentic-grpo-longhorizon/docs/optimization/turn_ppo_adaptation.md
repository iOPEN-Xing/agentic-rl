# Turn-PPO Adaptation for τ-bench

## Scope

Replace the current scheme-one training path (`turn heuristic reward + trajectory
GRPO`) with a faithful Turn-PPO path while preserving the existing actor model,
rollout backend, GPU topology, and τ-bench task configuration.

The implementation is grounded in:

- Turn-PPO, Sections 2.3–2.4:
  https://arxiv.org/html/2512.17008v2
- The paper's declared training-system base, RAGEN:
  https://github.com/RAGEN-AI/RAGEN (inspected at
  `20daedc47558e000f7de912b060646bf2e8026bd`)
- The vendored veRL actor, critic, rollout, and policy-loss interfaces in this
  repository.

The Turn-PPO paper does not publish a standalone code repository or a public
Turn-PPO branch. RAGEN is therefore used as the upstream systems reference; the
paper equations are the algorithmic source of truth.

## Algorithm Contract

### Turn MDP

One turn is one complete assistant generation:

```text
state s_t = full history + latest user/tool observation
action a_t = all tokens generated by the assistant in that generation
```

A τ-bench reset observation is the first user query and is injected into
`s_1`; the parquet's system-only prompt is not treated as a complete task
state.

A tool result or user reply starts the next state. Multiple tool calls separated
by tool outputs are therefore multiple turns, not one user-level macro turn.
If a tool transition terminates τ-bench, the action that invoked that tool is
the final assistant turn; the loop must not generate an extra response from an
already-terminal environment.

### Reward

The first comparison baseline uses the native τ-bench trajectory score only:

```text
r_t = 0, t < T
r_T = τ-bench terminal score
```

The existing PRM-Lite and potential-shaping code is left in place for historical
ablations but is disabled in the Turn-PPO configuration and is not part of the
algorithmic correctness claim for this baseline.

### Critic and Turn GAE

The critic value for turn `t` is read at the first assistant token position.
Because veRL shifts critic outputs by one token, that position is conditioned on
the complete state immediately before the assistant action.

```text
delta_t = r_t + gamma * V(s_{t+1}) - V(s_t)
A_t = delta_t + gamma * lambda * A_{t+1}
```

The same `A_t` is assigned to every assistant token in the turn. Critic loss is
computed only at turn starts and is averaged per trajectory over turns.

### Actor Objective

For each assistant turn:

```text
rho_t = product_k exp(log pi_new(a_tk|.) - log pi_old(a_tk|.))
```

PPO clipping is applied once to `rho_t`, so the complete response is clipped as
one action. Following Table 1, turn losses are summed and divided by the total
number of assistant tokens in that trajectory, then averaged across
trajectories. The turn ratio already carries the summed token gradients for its
response, so replacing this denominator with a turn mean would over-scale long
responses. Token-level clipping is not used for the Turn-PPO policy term.

Token-level entropy and reference-model KL regularization are retained to keep
the existing comparison setup unchanged.

The strict baseline does not stack token/sequence rollout-IS, rejection
sampling, or the rollout-correction policy-gradient objective on top of this
loss. Those corrections have a different aggregation contract and would no
longer be the Turn-PPO objective above. Bypass mode is used only to take the
rollout log-probability as `pi_old`.

### Equal-budget sampling

The GRPO config collected `4 tasks × 8 rollouts = 32 trajectories` per update.
Turn-PPO does not need within-task groups, so the same trajectory budget is
reallocated to `32 tasks × 1 rollout`. This follows the paper's PPO recipe,
increases critic state diversity, and preserves the sampling-budget basis of
the cross-scheme comparison. The actor/critic learning rates are the reported
`1e-6`/`1e-5` pair.

## Implementation Tasks and Acceptance Criteria

### Task 1: Rollout turn identity

- Every assistant generation has one non-overlapping response span.
- Every trainable response token has exactly one positive `turn_id`.
- User/tool/padding tokens have `turn_id == 0`.
- Spans are clipped safely when the response limit truncates a generation.

Verification:

```bash
pytest -q verl/tests/experimental/agent_loop/test_turn_ppo_utils.py
```

### Task 2: Turn-level advantage and critic targets

- Terminal score is assigned to the final assistant turn.
- GAE recurs over turns, not tokens.
- Advantage is constant within a turn and zero on environment tokens.
- Critic targets and masks exist only at turn starts.
- Each trajectory contributes equal total critic weight independent of its
  number of turns.

Verification:

```bash
pytest -q verl/tests/trainer/ppo/test_turn_ppo_on_cpu.py -k gae
```

### Task 3: Turn-level PPO loss

- Importance log-ratios are summed across each assistant response.
- PPO clipping occurs once per turn.
- Turn losses are summed and normalized by the trajectory's assistant-token
  count exactly as in the paper objective.
- Missing or malformed turn identity fails loudly.

Verification:

```bash
pytest -q verl/tests/trainer/ppo/test_turn_ppo_on_cpu.py -k policy
```

### Task 4: Trainer and configuration wiring

- `turn_gae` enables the critic and consumes `turn_ids`.
- Critic update uses the turn-start value mask.
- Actor update selects and forwards `turn_ids`.
- Scheme-one config selects `turn_gae` and `turn_ppo`.
- Rollout IS/RS and the rollout-correction policy-gradient loss fail
  configuration validation for this strict baseline.
- Existing GPU counts, actor model path, rollout backend, tensor parallelism,
  and actor LoRA settings are unchanged.
- Per-update rollout count remains 32 while PPO uses one rollout per task.

Verification:

```bash

```

## PRM-Lite Tool-Call Correctness Audit

This audit is a future-run correction in `codex/turn-level-reward`. It does not
modify or restart the active `prm_lite_lata` process in the main worktree, and
it does not change the strict Turn-PPO configuration's binary terminal reward.

### Observed failure

The active run's `experiments/prm_lite_lata/training.log` was inspected through
step 199. It contained 69 unknown-tool attempts and 14 Hermes decode failures:

| Approximate rollout step | Unknown tool | Malformed call |
| --- | ---: | ---: |
| 1-100 | 24 | 5 |
| 101-199 | 45 | 9 |

The most frequent unknown names were `update_reservation_payment` (24),
`create_user` (18), `update_reservation_payment_methods` (10), and
`search_multistop_flight` (6). None is present in the authoritative 14-tool
airline YAML or `AIRLINE_TOOL_NAMES`, so this is policy hallucination rather
than a missing schema registration.

Two observability gaps prevented the intended PRM behavior:

1. Hermes logged and discarded calls that remained malformed after repair.
2. Unknown calls returned a tool error but were not added to the tau-bench
   `action_history`. The scorer therefore could not penalize the action itself.

### Correction and reward contract

- Hermes emits a diagnostic `FunctionCall` for an unrecoverable malformed
  block, allowing the normal tool-response path to return a recoverable error.
- Malformed arguments and unknown names are recorded as `is_error=True`
  actions with their model-generated name, parsed parameters where available,
  bounded raw diagnostics, and assistant content.
- These cases remain `valid_for_training=True`: they are attributable policy
  errors. Tool runtime, environment, release, interaction, and score failures
  remain infrastructure failures and are excluded with a zero response mask.
- Invalid attempts count toward the trajectory's tool-attempt budget but never
  call `env.step`, never add environment reward, and never alter terminal
  outcome computation.
- PRM-Lite applies a direct `-0.10` per-action process penalty. Under the
  existing `outcome + 0.3 * process` formula, an isolated invalid action
  changes total reward by `-0.03`; the outcome term remains unchanged.

The `-0.10` magnitude is a conservative engineering default aligned with the
existing premature-escalation penalty, not a claimed optimum. A later controlled
ablation should compare error rate, task success, process-score variance, and KL
before changing it. The action-recording and policy/infrastructure distinction
are correctness requirements independent of that tuning choice.

### CPU validation

No CUDA context, model weights, vLLM server, or training process was started.
The parser, policy-error, PRM-Lite, trajectory-validity, Turn-PPO math, and
metric suites passed 84 tests; the algorithm/config suite passed 9 tests, for
93 CPU tests in total. The Hydra config test must be run from the vendored
`verl` directory because it resolves `verl/trainer/config` relative to the
process working directory.

Additional checks passed:

- `bash -n` for the training and evaluation launchers.
- `git diff --check`.
- Hydra resolution of `turn_ppo/turn_gae`, both vanilla parquet paths, and
  the unchanged model/LoRA/TP/GPU/learning-rate invariants.
- Exact `env`, `policy`, and `eval` section equality between all four
  Turn-PPO checkpoint configs and their vanilla-main counterparts.

## Non-goals

- Running training, loading model weights, or allocating GPUs.
- Tuning actor/critic learning rates or memory placement.
- Adding judge, TRACE, PRM, or potential-shaping signals to the primary
  Turn-PPO baseline.
- Changing the other two comparison branches.
