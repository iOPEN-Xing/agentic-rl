01 · 背景

长程 Agent 可能调用几十到上百次工具

终局正确性仍然可靠，但随着轨迹变长，它会变得极度稀疏、方差高，无法解释中间动作。

02 · 矛盾

失败轨迹里也可能有大量正确动作

一次错误结论会让 outcome-only 训练惩罚整条轨迹，连早期找到关键证据的搜索也一起被否定。

03 · 方法

Gold 概率 → Log-Ratio Value → TD Credit

冻结模型为每个工具边界的前缀打分；相邻价值差生成 Turn credit，再与 GRPO 终局优势联合优化。

04 · 本项目结论

可以适配，但不能沿用旧分支的环境 MC reward

当前代码已改为 canonical Gold Target + frozen-reference prefix scoring + log-ratio TD；真实收益仍须先过离线归因门槛，再做小权重在线消融。

阅读路径：问题与论文公式 → 旧分支为何不等于 TRACE → 当前代码如何生成 Gold Target 和 prefix score → task 0 六轮订票逐步拆解 → 论文差异、风险与上线验收。

01 · Problem

终局奖励能判断“对不对”，却不知道“哪一步开始变对”

在深度搜索中，早期 query、打开哪篇文档、在文档里找哪个关键词，都会改变后续证据。最终答案错了，并不意味着这些动作都没价值；最终答案对了，也不意味着每次工具调用都值得强化。

训练 Process RM

能给细粒度监督，但需要额外标注、合成 step label 或训练一个专门评估器。

训练 Critic

能估计状态价值，但长轨迹的稀疏终局回报会让 critic 本身难学，且增加模型与显存成本。

TRACE

不训练新评估器；让冻结 Reference Model 只回答一个更窄的问题：当前前缀让已知 Gold Answer 变得多可预测？

02 · Method

方法全景：Reference Model 是探针，不是 Judge

TRACE 不让 Reference Model 直接判断动作好坏，也不让它生成自然语言评分。它只计算 Gold Answer 在每个轨迹前缀下的平均 log-probability，再把“距离可预测还差多少”转换为状态价值。

三条公式抓住 TRACE

$$\bar{\ell}_k=\frac{1}{|y^\star|}\sum_{t=1}^{|y^\star|} \log\pi_{\mathrm{ref}}(y^\star_t\mid S_k,y^\star_{<t}), \qquad d_k=-\bar{\ell}_k+\epsilon$$

怎么读：用 teacher forcing 测量 Gold Answer 在当前前缀下的平均 log-probability；$d_k$ 是“剩余答案似然 gap”。公式中的小于号已做 HTML 转义。

$$V(S_k)=\log\frac{d_0}{d_k},\qquad \delta_k=V(S_{k+1})-V(S_k)=\log\frac{d_k}{d_{k+1}}$$

怎么读：如果这次工具调用让剩余 gap 减半，$\delta_k=\log 2$；gap 不变则为 0，gap 变大则为负。

$$c^{(K)}_{g,k}= \frac{\sum_{u=k}^{h_{g,k}}\gamma_{\mathrm{td}}^{u-k}\delta_{g,u}} {\sum_{u=k}^{h_{g,k}}\gamma_{\mathrm{td}}^{u-k}},\quad r^{\mathrm{turn}}_{g,k}=c^{(K)}_{g,k} +\mathbf 1[h_{g,k}=T_g-1]\lambda_{\mathrm{term}} \gamma_{\mathrm{td}}^{T_g-k}A_g^{\mathrm{out}}$$

实现参数：论文主实验与当前配置均为 $\epsilon=0.1$、$K=3$、$\gamma_{\mathrm{td}}=0.8$、$\lambda_{\mathrm{term}}=2.0$。分母 $Z$ 不能漏；terminal fill 的指数是 $T_g-k$，最后一个工具 Turn 仍折扣一次。

$$\hat A_{g,t}=\alpha_{\mathrm{out}}A_g^{\mathrm{out}} +\alpha_{\mathrm{turn}}r^{\mathrm{turn}}_{g,\mathrm{turn}(t)}$$

怎么读：每个 assistant 决策 Turn 的 policy token 同时接收终局组相对优势和本 Turn 的局部信用；tool/user observation token 被 mask；两个权重决定“最终答对”和“局部进展”各占多大影响。

为什么冗余调用不能刷分：one-step credit 会 telescope：$\sum_k\delta_k=V(S_T)-V(S_0)$。在起点和终点相同的情况下，多插几个无用步骤不会增加总信用。实际方法再加入 K-step backup 与 terminal fill，以换取延迟证据传播和终局锚定。

源码状态（核验日期：2026-07-30）：arXiv 摘要页与正文没有提供作者代码仓库；页面只给出论文、PDF 与 TeX source。因此本项目实现是依据论文 Algorithm 1、公式 (5)–(12) 和 Appendix A.1 重建，不应宣称为“官方代码移植”。报告中所有实现差异都单独列出。

算法执行顺序：从一组 rollout 到策略更新 展开查看 TRACE 的最小实现骨架；重点是 Reference Model 的批量前缀打分。 
sample G trajectories for the same prompt
compute terminal rewards and group-normalized outcome advantages

for each trajectory:
    split prefixes at decision/observation boundaries
    score the gold answer under the frozen reference model
    convert scores to log-ratio state values
    compute one-step TD deltas and K-step turn credit

mix outcome advantage with turn credit
update the policy with a clipped objective

03 · Engineering landing

旧分支为什么不准确，以及当前实现如何闭环

原方案三分支虽然名为 Hybrid Advantage，但使用的是 τ-bench incremental reward 的 MC reward-to-go，再按相同 Turn 跨 rollout 标准化，并让训练后期逐步降低 session 权重。这不是 TRACE；更关键的是，τ-bench 原生环境在非终止步骤通常返回 0，根本不能提供预期的密集进展信号。

边界定义是一次有意、可审计的任务适配

论文：tool-only transition

每个 assistant Turn 要么调用一个 browser tool，要么输出 final answer，因此工具边界天然等于决策边界。

本项目：decision–observation transition

航空任务还包含纯对话澄清。当前实现把“assistant 决策 → tool observation 或 user reply → 下一次 assistant 生成前”作为状态转移；最后一次 assistant 回复只接收 outcome，不伪造一个不存在的后继状态。

这不是无条件可用：结构化 JSON 比论文的短答案长，固定字段名和标点可能稀释真正的业务信息。上线训练前必须在历史轨迹上验证：正确航班搜索、有效澄清、用户信息读取、成功写操作是否总体提高 $\bar\ell$；错误支付、重复调用、错误写入是否降低它。过不了这道离线门槛，就应回退 outcome-only GRPO，而不是调大 turn weight。

最关键的理论外推：Task.actions 描述 verifier 要看到的终局数据库变化，并不是每个 prefix 后唯一正确的“下一条 assistant 回复”。完整 JSON 里还会包含已经执行过的 action，而模型原生 tool-call 格式也未必等于这份序列化。因此它只能作为固定的任务完成记录来探测 progress，不能当 behavior-cloning label；若冻结模型主要在响应 JSON 格式，而不是在响应业务事实，$\delta_k$ 就没有可用的信用含义。离线校准应优先比较完整 JSON、压缩 value-bearing target 与 tokenizer 原生 tool-call skeleton，并要求 target 在所有 prefix 上保持完全相同、始终不进入 actor prompt。

这里后段 Turn credit 大，并非算法规定“越晚越重要”，而是示例 prefix 在拿到付款 id 和成功写 DB 后关闭了更多剩余 gap，同时 K-step terminal fill 只覆盖能看见轨迹末端的窗口。若某次搜索引入错误信息，$\bar\ell$ 变得更负，$\delta$ 会自然为负。

真实错误恢复：不要把每次 tool error 硬编码成负奖励

同一 task 的历史 sample_idx=15 首次预订把付款写成 $250+$55，总额 $305，与票价 $255 不符；工具返回 Error: payment amount does not add up。随后 actor 修正为 $250+$5 并成功。TRACE 的合理行为是：错误 observation 可能降低 target likelihood，修正动作再显著提高；最终 verifier 仍给成功 rollout 正 outcome。若用规则直接把任何 error 永久判负，会误伤“可恢复探索”，这正是当前实现不再消费 handcrafted incremental reward 的原因。

核心公式在代码中的最小可运行形态 省略输入检查；真实实现包含 shape、有限值、mask、span 对齐和 context length 校验。 
remaining_gap = -avg_gold_log_probs + gap_epsilon
state_values = torch.log(remaining_gap[0] / remaining_gap)
deltas = state_values[1:] - state_values[:-1]

for k in range(num_transitions):
    h = min(k + td_horizon - 1, num_transitions - 1)
    discounts = td_gamma ** torch.arange(h - k + 1)
    local = (discounts * deltas[k:h + 1]).sum() / discounts.sum()
    terminal = (
        terminal_scale * td_gamma ** (num_transitions - k) * outcome_adv
        if h == num_transitions - 1 else 0.0
    )
    turn_reward[k] = local + terminal

advantage_on_turn_k = outcome_weight * outcome_adv + turn_weight * turn_reward[k]

数字很强，但适用边界也很清楚

  • 受控比较：GRPO、GSPO、GiGRPO 与 TRACE 使用相同骨干、浏览工具、数据、终局奖励和评测接口，差异主要来自 credit signal。
  • 迁移证据：训练发生在 closed synthetic search，提升仍迁移到 BrowseComp、GAIA 与中文 xbench-DeepSearch。
  • 训练配方：没有 cold-start SFT、agentic mid-training、live-web training、强 Judge 或训练好的 process reward model。
  • 统计边界：论文说明受控消融通常是单次训练运行，小差异应理解为方向性结果，而不是已校正方差的定论。

07 · Decision & acceptance

最终判断：理论链已经正确，数据代理仍需先证伪后训练

代码层面

当前分支不再把环境 reward、potential 或 MC return 冒充 TRACE。Algorithm 1 的核心公式、mask、数据 target 与 frozen-ref scoring 已形成完整接线。

理论层面

TRACE 的 policy invariance 并非自动保证；它是一个辅助代理目标。one-step telescoping 只约束累计局部 credit，不证明 JSON likelihood 等价于真实业务进展。

数据层面

τ-bench 的 actions/outputs 能提供 verifier-aligned target，因此比“预订成功”这类弱文本更合理；但目标较长、任务仅 50 个，过拟合 task-specific value tokens 是主要风险。

先离线、再在线的五道验收门

顺序必须回答的问题建议指标失败动作
1 · Target validity同一 task 的正确 prefix 是否比错误 prefix 更容易预测 canonical target？pairwise ranking accuracy；成功/失败 endpoint AUC；按 task bootstrap CI改 target 表达；仍不稳定则停用 TRACE
2 · Local attributioncredit 方向是否符合真实动作语义？正确搜索、澄清、read→write chain、错误写入、恢复操作的人工盲审一致率调整 boundary/target，不得先调大权重
3 · Safety更高 likelihood 是否诱导未确认写操作或参数猜测？wrong write、write-tool error、未确认 booking/cancel/update、transfer rate安全项变差即阻断
4 · Generalization收益是否只记住 seen 40 tasks？unseen 10 tasks pass@1 / pass^k；按 booking/change/cancel/read-only 分桶；多 seed CI只 seen 提升不接受
5 · Efficiency额外 ref forward 是否换来值得的成功率？success-conditioned turns/tokens、scored prefixes、ref scoring wall time、OOM/超长比例收益不足则回退 outcome-only

最小消融矩阵

  1. Baseline：现有 outcome-only GRPO，保持全部 rollout/模型/数据配置一致。
  2. TRACE-core：$\alpha_{turn}=0.2,K=3$，当前实现；这是主比较。
  3. 无 TD：$K=0$，只保留 outcome 与末端锚，检验 prefix TD 是否真正贡献。
  4. 权重敏感性：$\alpha_{turn}\in\{0.05,0.1,0.2\}$；不建议直接测试大权重，论文也显示过大会退化。
  5. 边界敏感性：tool-only vs tool+user clarification；这是 τ-bench 特有的关键消融。
  6. Target 敏感性：完整 canonical JSON vs 压缩 value-bearing target vs tokenizer 原生 tool-call skeleton；用于区分业务进展信号与固定 schema / 格式似然。

Go / No-Go：现在可以进入“离线 reference scoring 校准”阶段，但还不能据此宣称方案三已在 τ-bench 有效。只有 unseen success 在多 seed 下提升，同时 wrong-write、tool-error、transfer 和成功条件成本不恶化，才进入正式训练结论。任何情况下，Reference Model 都不能替代 DB hash、required output 和用户确认所组成的终局 verifier。
