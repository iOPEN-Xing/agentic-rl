3基线问题分析

3.1 失败案例剖析

典型失败案例：支付方式错误 (TOOL_CALL_ERROR)

# 用户提供了具体的支付偏好
User: "I want to use my two certificates to pay..."

# Agent 尝试了多个不存在的支付方式 (循环错误)
Agent: Tool: book_reservation(payment=[certificate_345678, ...])
Error: payment method certificate_345678 not found

Agent: Tool: book_reservation(payment=[certificate_987654, ...])
Error: payment method certificate_987654 not found

# 反复尝试8次，最终任务失败

# 结果：reward = 0，agent 不知道哪一步出了问题

3.2 问题根因：Session-End Only Reward

核心问题：当前系统只在 session 结束时计算 reward
  • Credit Assignment 困难：无法知道是哪一步出了问题
  • 学习信号稀疏：12轮对话只有1个reward信号
  • 错误难以纠正：agent不知道哪一步应该改变

3.3 问题的数学形式化

设一个 trajectory 为 $T = (s_0, a_0, r_1, s_1, a_1, r_2, ..., s_T)$，当前只有 $r_T$ 有意义：

$R(T) = r_T = \begin{cases} 1 & \text{task completed} \\ 0 & \text{task failed} \end{cases}$

对于长度为 T=12 的 trajectory，agent 无法区分：

  • 第3步的搜索参数错误 → 导致后续全部失败
  • 第7步的支付方式错误 → 只有最后一步有问题
  • 第10步的理解偏差 → 大部分行为是正确的

4方案一：Turn-Level Reward Signal

技术报告参考

本方案基于以下技术报告，详细的公式推导和实验分析请参阅：

📄 Turn-PPO 技术报告 📑 原论文

4.1 核心思想

在每个 user turn 结束后立即计算 reward，而不是等到 session 结束：

User Turn 1
→
Reward₁
→
Tool Call
→
Reward₂
→
User Turn 2

对比传统方式：整个 session 只在最后有一个 reward。

4.2 奖励函数设计

4.2.1 三层奖励结构

$r_{turn} = r_{env} + r_{prm} + r_{shaping}$
奖励类型 来源 计算方式 示例
$r_{env}$ 环境验证 规则匹配 工具调用成功 +0.1
$r_{prm}$ 过程奖励模型 LLM 判断 提供了有用信息 +0.05
$r_{shaping}$ 势函数 进度估计 接近目标 +0.03

4.2.2 环境奖励规则（航空订票场景）

def _compute_turn_reward(state: dict, turn_idx: int) -> float:
    """每个 user turn 后立即计算 reward"""
    reward = 0.0
    last_action = state.get("last_action")

    # 1. 工具调用成功
    if last_action:
        if last_action.get("is_error") == False:
            reward += 0.1  # 成功执行

        tool_name = last_action.get("tool")

        if tool_name == "search_direct_flight":
            # 检查是否满足用户的时间约束
            if _check_departure_time_constraint(last_action, state):
                reward += 0.05

        elif tool_name == "book_reservation":
            if _validate_payment_methods(last_action, state):
                reward += 0.15
            else:
                reward -= 0.05

    # 2. 势函数 Shaping
    potential = _compute_potential(state, turn_idx)
    prev_potential = state.get("prev_potential", 0)
    if turn_idx > 0:
        shaping = 0.99 * potential - prev_potential
        reward += shaping
    state["prev_potential"] = potential

    return reward

典型对话的 Reward 序列

Turn 1 Agent: search_direct_flight +0.1 工具调用成功
Turn 2 Agent: 筛选11AM后航班 (参数错误) -0.05 参数不被支持

... ... ...
Turn 10 Agent: book_reservation (支付错误) -0.1 支付失败

最终结果：Session Reward = 0 (失败)

Turn Rewards = [+0.1, -0.05, +0.05, +0.1, ..., -0.1]

4.4 势函数 Shaping 的数学保证

Potential-based reward shaping 满足策略不变性：

$r'(s, a, s') = r(s, a, s') + \gamma \phi(s') - \phi(s)$

其中 $\phi$ 是势函数。这个变换保证最优策略不变（Ng et al., 1999）。

class EnhancedUserSimulator:
    """
    增强版用户模拟器：同时生成回复和评估

    def generate_response_and_judge(
        self, agent_message, task_context, conversation_history
    ) -> tuple[str, dict]:

        # 1. 生成用户回复
        user_response = self._generate_user_response(...)

        # 2. 生成 judge 反馈
        judge_feedback = self._judge_agent_performance(...)

        # 3. 构建 reward signal
        reward_signal = {

$r_{final} = w_1 \cdot r_{env} + w_2 \cdot r_{judge} + w_3 \cdot r_{prm}$

$w_2 = 0.3$ LLM Judge Reward 软评价，可作为补充

6.2 两种 Advantage 的对比

维度 Session-Level (GRPO) Turn-Level (TD)
计算方式 Group 内相对比较 TD error 累积
优点 稳定、易实现 细粒度 credit assignment
缺点 无法区分 turn 差异 可能不稳定
适用场景 短轨迹、简单任务 长轨迹、复杂任务

6.3 公式推导

6.3.1 Session-Level Advantage (GRPO)

对于同一 task 的多个 sample，计算相对 advantage：

$A_{session}^{(i)} = \frac{R^{(i)} - \mu_{task}}{\sigma_{task} + \epsilon}$

6.3.2 Turn-Level Advantage (TD)

使用 TD error 分解每个 turn 的 contribution：

$\delta_t = r_t + \gamma V(s_{t+1}) - V(s_t)$
$A_{turn} = \sum_{k=0}^{T-t-1} \gamma^k \delta_{t+k}$

6.3.3 Gated Fusion

自适应融合两种 advantage：

$A_{final} = \alpha \cdot A_{session} + (1-\alpha) \cdot A_{turn}$

其中 $\alpha$ 根据训练进度自适应调整：

$\alpha = 0.8 - 0.6 \cdot \frac{step}{total\_steps}$   (线性衰减)

6.4 实现代码

def compute_grpo_hybrid_advantage(
    token_level_rewards, response_mask, index, turn_boundaries, config
) -> tuple:
    """
    Hybrid Advantage Estimation
    1. Session-level: GRPO group normalization
    2. Turn-level: TD-style credit assignment
    3. Gated fusion: adaptive alpha schedule
    """

    # Step 1: Session-Level Advantage (GRPO)
    scores = token_level_rewards.sum(dim=-1)
    grpo_adv = torch.zeros_like(scores)
    for idx in id2score:
        scores_group = torch.stack(id2score[idx])
        mean, std = scores_group.mean(), scores_group.std() + 1e-6
        grpo_adv[mask] = (scores[mask] - mean) / std

    # Step 2: Turn-Level Advantage (TD)
    turn_adv = compute_turn_level_advantage(
        token_level_rewards, turn_boundaries, gamma=0.9
    )

    # Step 3: Gated Fusion
    alpha = compute_alpha_schedule(config)  # 前期偏session，后期偏turn
    final_adv = alpha * grpo_adv + (1 - alpha) * turn_adv

    return final_adv * response_mask, final_adv * response_mask

7.2 验证脚本

class ExperimentValidator:
    def validate_reward_signal(reward_data: dict) -> bool:
        checks = {
            "sparsity": self._check_reward_sparsity(reward_data),
            "distribution": self._check_reward_distribution(reward_data),
            "correlation": self._check_session_turn_correlation(reward_data),
        }
        return all(checks.values())

    def _check_reward_sparsity(reward_data) -> bool:
        avg_rewards = np.mean([len(r) for r in reward_data["rewards_per_trajectory"]])
        return 3 <= avg_rewards <= 10

    def _check_reward_distribution(reward_data) -> bool:
        all_rewards = [r for rs in reward_data["rewards"] for r in rs]
        return any(r > 0 for r in all_rewards) and any(r < 0 for r in all_rewards)
