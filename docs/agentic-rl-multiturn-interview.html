01 · Mental model

面试先给结论：Agentic RL 不是“给 Agent 一个奖励”

Agent 在多轮任务中持续观察用户、工具和数据库反馈，之后再决定下一步。因此它不是一次生成、一次打分的 contextual bandit，而是带有部分可观测性、长时延结果和环境副作用的序列决策问题。真正困难的是：如何定义一步、如何验证成功、如何把终局结果归因给中间决策，以及如何在策略分布变化时稳定更新。

一句话：User Simulator 决定“训练时会遇到怎样的用户”，Verifier 回答“最后做对没有”，PRM/Credit Estimator 回答“哪一步值得鼓励”，Policy Optimizer 再决定“怎样把这些信号稳定地变成参数更新”。
1

Environment / User

用户模拟器、工具和数据库共同定义转移分布。Simulator 是否泄露、过度配合或缺乏真实噪声，会直接改变 policy 学到的最优行为。

2

Verifier / Reward

由规则、数据库终态或可执行测试判断业务是否完成。它应尽量客观、抗 reward hacking，并与线上成功条件一致。

3

PRM / Credit Assignment

把轨迹级结果解释到 Turn：可以来自 learned critic、规则增量奖励、冻结参考探针，或专门学习动作 promise/progress 的过程奖励模型。

4

Policy Optimization

使用 PPO/GRPO 比率、clipping、KL、mask 与归一化进行更新，并控制 rollout policy 与当前 policy 的偏差。

真正决定上限的是五个彼此耦合的模块

Policy ceiling

基座模型的推理、工具 schema 理解、长上下文与错误恢复能力，决定可探索行为的支持集。

Simulator ceiling

训练 policy 实际优化的是 $P_{\mathrm{sim}}$ 下的回报；模拟用户若过度合作，线上真实用户一犹豫、纠正或表达含糊，策略就会失配。

Verifier ceiling

若最终状态、政策合规或必要输出没有被准确校验，再好的优化器也只会把 verifier 漏洞放大。

PRM / credit ceiling

过程信号若把“形式上像进展”误当“真实进展”，会产生 shortcut；若过于稀疏，又无法区分失败轨迹中的好动作。

Optimization ceiling

mask、behavior log-prob、ratio、group normalization、policy lag 与长度归一化决定正确监督能否不失真地进入梯度。

最常见的概念混淆：增加一个中间 reward 并不自动解决局部 credit；把 Judge 分数写在某个 Turn 的 token 位置，也不代表标准 GRPO 会产生 Turn 级优势。如果训练器先把所有 token reward 求和为一个轨迹标量，再对所有 assistant token 广播同一个 group advantage，局部位置信息已经消失。

为什么多轮 Agent 比普通 RLHF 更难

交互改变后续数据分布

一次错误澄清、错误检索或错误写操作会改变后续 observation；样本不再是静态 prompt-response pair。

奖励延迟且轨迹变长

τ-bench 常在数据库最终状态才给 0/1。成功依赖多个前置步骤，失败轨迹中也可能包含大量正确动作。

环境不是语言模型

工具 schema、业务规则、幂等性、权限、超时和重置语义都会影响训练；只优化自然语言质量无法保证任务完成。

02 · Formalization

先把一步切对：多轮交互最好建模为 Turn-MDP / POMDP

对于事务型 Agent，外部真实状态包含用户隐藏目标、数据库与工具后端；模型只能通过对话历史和工具返回间接观察它，因此严格说更接近 POMDP。训练实现通常把完整可见历史作为信息状态，得到一个可操作的 Turn-MDP。

$$s_t=(x,\;a_1,o_2,\ldots,a_{t-1},o_t),\qquad a_t=(y_{t,1},\ldots,y_{t,L_t}),\qquad \tau=(s_1,a_1,r_1,\ldots,s_T,a_T,r_T)$$

语义：$s_t$ 是第 $t$ 次模型决策前可见的完整历史；$a_t$ 是本轮完整 assistant response，而不是单个 token；$o_{t+1}$ 可能来自用户、工具或环境。只有 assistant action token 进入 policy loss，用户与工具 observation 只作为条件上下文。

标准 outcome-only GRPO 做了什么

对同一任务采样 $G$ 条轨迹，用终局结果在组内标准化，再把同一个轨迹优势广播给该轨迹所有策略 token：

$$A_g^{\mathrm{out}}= \frac{R_g-\operatorname{mean}(R_{1:G})} {\operatorname{std}(R_{1:G})+\epsilon}, \qquad \hat A_{g,t,k}=A_g^{\mathrm{out}}$$

优点：不训练 critic，结果可验证时简单稳健。局限：同一轨迹里，正确检索、错误参数、错误恢复和最终提交拿到相同优势；如果一组 rollout 全成或全败，组内方差不足，学习信号还会接近 0。

粒度“一步”是什么优势信号主要问题
Token-MDP一个 token可在 token 级变化语言 token 不是独立业务决策；序列很长，critic 与 bootstrapping 难度大。
Trajectory / bandit整条会话整轨迹一个优势简单，但完全忽略中间状态转移与局部贡献。
Turn-MDP一次完整模型响应同一 Turn 内一致、Turn 间可不同更匹配 Agent 决策语义；需要可靠边界与新的 credit estimator。

面试加分点：“Turn-level”描述的是决策/优化粒度，不等于“每轮人工造一个 reward”。严格 Turn-PPO 可以只使用终局 0/1 reward，局部差异由 critic 的 TD/GAE 学出来；UserRL 则要求环境本身提供可信的逐 Turn 增量反馈；TRACE 用 reference score 构造局部代理信号。三者的监督来源不同。

04 · Three methodologies

三个方案不是同义改写，而是三种不同的“局部证据来源”

原始方案文档提供了三条探索路线，但后续技术报告已经校正了其中最重要的概念边界：方案一应落为严格 Turn-PPO；方案二必须把 User Simulator 与 Judge 分开；方案三不能沿用手工 potential 或环境 Monte Carlo，而应实现 TRACE 的 frozen-reference log-ratio TD。

Critic-based

Turn-PPO

在每个 Turn 决策边界学习 $V_\phi(s_t)$，用终局 reward 的 TD/GAE 把信用传回不同 Turn，再以整段 response 的概率比做 PPO clipping。

它回答：从历史数据看，当前状态未来成功概率有多大？

Environment-grounded

UserRL

由 Gym/规则系统产生逐 Turn 增量 reward，再独立做 turn reward mapping 与 trajectory scoring。用户模拟器负责互动，不负责裁判。

它回答：环境规则能否直接验证本轮取得了什么进展？

Reference-based

TRACE

冻结 reference model，在每个前缀后 teacher-force canonical gold target；目标变得更容易预测，就视为关闭了部分剩余 gap。

它回答：本轮 observation 是否让正确目标更可预测？

方案一：Turn-PPO——让 critic 学习 Turn 级归因

$$\delta_t=r_t+\gamma V_\phi(s_{t+1})-V_\phi(s_t),\qquad A_t=\delta_t+\gamma\lambda A_{t+1}$$
$$\rho_t(\theta)= \frac{\pi_\theta(a_t\mid s_t)} {\pi_{\theta_{\mathrm{old}}}(a_t\mid s_t)} =\exp\!\left(\sum_{k\in a_t} [\log\pi_\theta(y_k)-\log\pi_{\mathrm{old}}(y_k)]\right)$$

同一 response 内 token 共用 $A_t$；不同 Turn 的优势可以不同。critic 只在 Turn 边界学习，轨迹内按 $1/N_i$ 归一化，避免长对话仅因 Turn 多而拥有更大 critic 权重。

对当前数据的判断：τ-bench 的规则终局 reward 可以直接作为 $r_T$，中间 $r_t=0$。这并不妨碍 Turn-PPO；critic 正是在相似任务与轨迹中学习哪些边界状态更可能成功。它适用当前数据与 veRL 框架，也是三条路线中最自然的主线。

核心风险：长 response 的 token ratio 连乘等价于 log-ratio 求和再指数化，方差可能很大；而二值终局 reward 对 critic 的监督也弱。应监控 ratio/clip fraction、value explained variance、Turn advantage 分布和策略坍缩。几何平均 ratio 可以作为稳定性消融，但不能与严格 Turn-PPO 基线混写。

方案二：UserRL——先问环境是否真的拥有 dense progress

$$R_{\mathrm{traj}}(\tau)=\operatorname{Score}(r_1,\ldots,r_T),\qquad \tilde r_t=\operatorname{Map}(r_t,\ldots,r_T)$$

UserRL 的关键是同一份规则增量 reward走两条独立路径：trajectory scoring 决定组内整轨迹排序；turn mapping（Equalized、Reward-to-Go、Exponential Mapping）决定轨迹内部如何分配局部信号。

必须说清：User Simulator 生成用户回复；规则 Gym / Verifier 生成奖励。让同一个 Qwen3-14B 既模拟用户又作为 LLM Judge，是本项目的扩展实验，不是 UserRL 原算法。如果标准 GRPO 最终仍把 Judge events 求成轨迹标量，它只是辅助 outcome shaping，不是严格 Turn credit。

当前分支的安全语义是：规则 outcome 始终是主奖励；LLM Judge 默认关闭，只作为 interaction-cycle 诊断信号。只有在与规则 outcome、人工抽检和错误类别完成校准后，才允许小权重注入，而且不能在 session 与 turn 两条路径重复计奖。

方案三：TRACE——用冻结模型测量“离正确目标还有多远”

$$\bar{\ell}_t=\frac{1}{|y^\star|}\sum_j \log\pi_{\mathrm{ref}}(y^\star_j\mid S_t,y^\star_{<j}), \quad d_t=-\bar{\ell}_t+\epsilon$$
$$V(S_t)=\log\frac{d_0}{d_t},\qquad \delta_t=V(S_{t+1})-V(S_t)=\log\frac{d_t}{d_{t+1}}$$

如果一次搜索或澄清让 canonical gold target 在 reference 下明显更容易预测，$d_{t+1}$ 下降，局部 TD credit 为正。reference 不是 Judge，只做 teacher-forced likelihood probe；终局规则 outcome 仍保留。

对当前数据的关键适配：$y^\star$ 不能只是用户自然语言意图，而应是 verifier-aligned 的 canonical action/output，例如确定排序的 JSON：航班、乘客、支付拆分、行李、保险与必要输出。否则 reference 学到的可能只是复述问题，而不是业务完成进展。

05 · Process reward model

PRM 不是“多加一个分数”，而是一套过程监督系统

在 Agent 场景中，PRM 的价值不是替代终局 verifier，而是在成功极稀疏、同一失败轨迹仍包含大量正确动作时，估计某个状态—动作前缀对未来成功的 promise，或本轮相对上一轮带来的 progress。它的上限取决于标签是否真实、评分是否对齐 Turn、信号是否正确接入训练器，以及是否经得住策略主动寻找漏洞。

工程命名必须诚实：当前仓库的 “PRM-Lite” 是有价值的规则式 process shaping baseline，但不是一个训练出来的 Process Reward Model。是否叫 PRM 不取决于函数返回了 process_score，而取决于是否存在过程标签、可泛化的评分模型、逐 Turn 对齐、校准指标与训练器消费路径。

Learned Agent PRM 到底应该预测什么

数学题常有明确的中间正确/错误；工具 Agent 的一步往往没有唯一答案。先查直飞还是先查中转可能都合理，真正要估计的是“这一步之后成功概率如何变化”。一种可执行的标签来自对同一个前缀采样 $K$ 个 continuation：

$$\widehat q_t= \frac{1}{K}\sum_{k=1}^{K} R_{\mathrm{verify}}\!\left(\tau^{(k)}_{t\rightarrow T}\right), \qquad r_t^{\mathrm{progress}}=\widehat q_t-\widehat q_{t-1}$$

Promise 与 progress：$\widehat q_t$ 是当前前缀还能成功的概率近似；差分表示本轮关闭了多少成功缺口。$K$ 太小方差很大，且 continuation policy 改变后标签会漂移，因此必须记录生成 policy/version，并定期刷新困难前缀。

除了绝对回归，更稳健的做法是对同一前缀构造“较好动作—貌似合理但错误动作”的 counterfactual pair，训练排序：

$$\mathcal L_{\mathrm{rank}}(\psi)= -\log\sigma\!\left( q_\psi(h_t,a_t^+)-q_\psi(h_t,a_t^-) \right)$$

当前 task 0 天然提供正负对：付款 250+5 对 250+55、根据搜索结果选择 HAT136+HAT039 对选择更贵或不满足时间的行程。排序标签可由工具执行与最终 verifier 构造，不必全部依赖 LLM 打标。

book(250+5)不同动作 + data chain，形成正向恢复正确写入数据库并满足终局约束强正 progress，同时保留 outcome=1

结论不是“删掉 recovery 奖励”：恢复确实是长程 Agent 的重要能力。问题在于规则特征必须与工具执行结果、业务 schema 和后续终态联合解释。最稳妥的分工是：Verifier/工具给可执行真值，规则给可解释先验，learned PRM 学组合与泛化，终局 outcome 防止过程模型把表面技巧当成功。

06 · User simulator

用户模拟器不是数据生成器，而是训练环境的转移核

在多轮 Agentic RL 中，Simulator 决定用户何时透露信息、如何表达歧义、是否纠正错误、会不会不耐烦以及何时结束。策略优化的不是抽象的“真实用户回报”，而是模拟分布下的回报；因此一个更强、更会完成任务的 LLM，并不自动是更忠实的用户模型。

$$u_{t+1}\sim P_{\mathrm{sim}}(\,\cdot\mid g,z,h_t,a_t\,),\qquad J_{\mathrm{sim}}(\pi)= \mathbb E_{\tau\sim P_{\mathrm{sim}},\pi} [R_{\mathrm{verify}}(\tau)]$$

$g$ 是隐藏业务目标，$z$ 是行为风格/耐心/主动性等潜变量。即使 verifier 完全正确，最大化 $J_{\mathrm{sim}}$ 也只保证对 $P_{\mathrm{sim}}$ 最优；当真实用户的 disclosure、纠正和终止行为不同，state occupancy 会变化，policy 可能失去已学捷径的支持。

Simulator 评估要从“像不像”升级到“是否产生正确下游能力”

语义忠实度

slot retention、未问先泄露率、goal drift、虚构信息率、矛盾率、stop correctness。硬约束可自动校验。

行为分布

主动性、合作度、耐心、表达长度、歧义、纠正、情绪和 abandon 分布，与真实会话或人工设定的目标分布比较。

下游效用

在 sim-A 训练后，分别到 sim-B、holdout prompts 和真人上测 pass@1/满意度；用 cross-play gap 检查 co-adaptation。

  1. 训练池：固定任务目标，随机化行为潜变量和表达器；easy→ambiguous→noisy→adversarial 做 curriculum，但不能篡改业务真值。
  2. 留出池：使用从未参与训练的 simulator model、prompt family 与真人片段，作为 sim-to-real 决策门。
  3. 版本控制：算法主实验固定 simulator 版本；升级 simulator 必须重新跑 outcome baseline，而不是把环境变化算作算法收益。
  4. 真人小样本：优先用于发现未建模行为与校准分布，不必一开始就大规模真人 RL。每个 simulator 版本都维护失败类型回放集。

三种闭环坍缩与对应防线

Actor ↔ PRM reward hacking

Actor 找到“反复读工具、写长解释、调用 think”之类的表面高分模式。防线是终局 verifier、对抗负例、PRM 版本冻结、OOD/不确定性门控和 component 日志。

Actor ↔ Simulator co-adaptation

Actor 学会触发特定 simulator prompt 的过度披露或固定措辞，训练 pass@1 升高但换模拟器即失效。防线是 simulator pool、行为随机化、holdout cross-play 与真人小样本。

PRM ↔ 数据选择偏差

PRM 只看旧 policy 的常见错误，新 policy 进入新区域后评分失真。防线是 replay、active sampling、当前 policy hard negatives、版本标记与跨 policy 校准。

工程上不要 joint-train，先做分阶段版本冻结

  1. Phase 0 · 环境锁定：固定 task split、Simulator v1、prompt/decoding、工具/DB 和 verifier，复现 outcome-only GRPO。
  2. Phase 1 · 过程数据：冻结 Actor checkpoint，收集多样轨迹、continuations 与 counterfactual；规则 PRM-Lite 仅作为弱标签/诊断。
  3. Phase 2 · PRM gate：训练 PRM 并在未见 task、未见错误和不同 policy 轨迹上校准；先做 best-of-N，确认排序确实提升 verifier outcome。
  4. Phase 3 · 单因素 RL：冻结 Simulator 与 PRM，只改变 credit/optimizer。PRM 先小权重，保留 Turn-PPO、TRACE、UserRL-style 独立基线。
  5. Phase 4 · Cross-play：冻结新 Actor，换 holdout simulator/prompt/model；若收益消失，优先修环境泛化而不是继续调 RL 超参。
  6. Phase 5 · 迭代：把新失败加入 PRM 与 simulator 行为覆盖，但每次只升级一个版本，并重新运行基准矩阵。

09 · Systems thinking

Agentic RL 的算法是否成立，取决于系统有没有守住数据语义

大模型 RL 的公式通常只占系统的一小部分。多轮 Agent 还需要 rollout engine、工具沙箱、用户模拟器、状态存储、Verifier、Reference/Critic、训练 worker 与版本同步。任何一个边界错位，都可能让“能跑”与“算法正确”完全分离。

Actor / Rollout Policy

采样 assistant response 与工具调用。必须记录生成时的 log-prob 和 policy version；训练期重新计算的是 current log-prob。

User + Tools + State

用户模拟器维护隐藏意图与 disclosure policy；工具执行可验证读写；数据库按 rollout 隔离。Simulator model/prompt/decoding 是环境版本的一部分。

Verifier / Reward

比较最终状态、要求动作与输出。工具“调用成功”不等于业务“完成正确”；应记录 component reward 与失败原因。

Reference Policy

在 PPO 中可用于 KL 锚定；在 TRACE 中用于 gold-prefix scoring。这是两个不同计算路径，不能复用名称后混淆语义。

Critic

Turn-PPO 中与 actor 对齐到 Turn 边界，预测未来回报。value mask 与 actor mask 不同，且需要独立监控校准。

Process Reward Model

读取 Turn prefix、动作和工具结果，输出 promise/progress 与不确定性。必须独立版本化，并区分离线 rerank、在线 reward 和风险 gate 三种用途。

Trainer

组 batch、算 advantage、ratio、clip/KL 和梯度。需要控制长度归一化、组退化、过期数据以及异常轨迹。

On-policy、PPO 复用与异步 staleness

PPO 通常被称为 on-policy 方法，但实践中会对同一批由 $\pi_{\mathrm{old}}$ 生成的数据做多个 mini-batch epoch，并依靠重要性比率和 clipping 限制更新。当 rollout 与训练异步时，实际生成策略可能比 current policy 落后多个版本，此时问题不再只是“多训练几轮”，而是 policy lag。

$$\rho=\exp(\log\pi_\theta(a\mid s)-\log\pi_{\mathrm{behavior}}(a\mid s))$$

必须使用真正生成该轨迹的 behavior log-prob。只拿一个固定 reference policy 替代 behavior policy 不能修正 rollout staleness；reference KL 与 importance correction 是不同问题。

Reward hacking 的五道防线

  1. 结果锚定：最终数据库状态与任务规则决定 outcome，不用模型自评分替代。
  2. 信号解耦：Judge、progress proxy、格式奖励分别记录，不能提前相加后失去可诊断性。
  3. 对抗评测：测试重复检索、无意义澄清、绕过写操作、格式投机、错误后放弃等策略。
  4. 分布外验证：按 task/user/constraint 组合做未见切分，并验证 retail 等跨域迁移，防止记忆固定动作模板。
  5. 交互防线：测试能否诱导 Simulator 提前泄露、替 Agent 计算或无条件同意；训练与评测使用不同 simulator family 做 cross-play。

10 · Evaluation

实验不能只看 reward 曲线，要同时证明算法健康与业务有效

面试中最有说服力的回答不是“我预计提升多少”，而是给出可归因的实验矩阵、失败判据和决策门。当前三种方案都没有理由直接承诺未经实测的 pass@1 增幅。

业务层

核心 unseen pass@1 / pass@k、规则 compliance、正确写操作率、错误恢复率、超时/循环、平均 Turn 与工具成本。

算法层

有效 reward group 比例、advantage std、KL、entropy、clip fraction、ratio quantiles、gradient norm、response length。

Credit / PRM 层

Turn critic 的 value calibration；TRACE 与真实进展相关性；PRM pairwise accuracy、Brier/ECE、continuation-success 相关性、最早错误定位与 OOD 不确定性。

Simulator 层

slot 泄露/漂移/幻觉、stop correctness、行为覆盖度；训练 simulator→holdout simulator→真人的 cross-play gap。

系统层

rollout/PRM/Judge 延迟与成本、tool error 类型、环境 reset 失败、policy/simulator/PRM version 分布、长轨迹截断。

什么时候值得上 Learned PRM

值得

终局 verifier 强但极稀疏；轨迹长、失败中有大量正确步骤；能低成本执行 continuation 或构造可验证 action pairs；推理阶段也需要 rerank/risk gate。

暂缓

Turn 边界和工具结果尚未结构化；Simulator/Verifier 还在频繁变化；现有规则事件没有离线相关性；数据只覆盖单一 policy 的少量成功轨迹。

使用顺序

先离线错误定位与 pairwise 排序，再 best-of-N，随后小权重 Turn credit，最后才考虑与 policy 交替迭代。每一步都保留 outcome-only 对照。

三者可以组合吗

理论上可以，例如终局 outcome + Turn critic，或 outcome + TRACE/PRM local credit。但组合不是越多越好：critic、PRM、TRACE 与规则事件可能重复解释同一证据、改变奖励尺度并破坏实验可归因性。正确顺序是先建立单独强基线，验证每个 local signal 与真实业务进展的相关性，再用固定权重或有安全约束的门控做组合消融。

Potential-based shaping 的边界：若希望保持最优策略不变，经典形式要求 shaping 仅由状态势函数差构成，例如 $F(s,a,s')=\gamma\Phi(s')-\Phi(s)$，且 $\Phi$ 不能偷看当前状态不可得的终局结果。把 total_reward >= 1 放入中间 potential 会造成 terminal outcome 泄漏，不再具备该不变性保证。

12 · Interview questions

高频追问：回答要同时覆盖理论、实现和业务

为什么标准 GRPO 不适合直接解决多轮 credit assignment？

核心不是 GRPO “不能训练”，而是它默认用整轨迹的组相对优势。同一条成功轨迹中所有策略 token 拿同一个 $A_g$，无法区分有效搜索、错误参数和错误恢复；全成或全败的组还会退化。它是强 outcome baseline，但不是局部归因算法。

Reward shaping 和 credit assignment 有什么区别？

Reward shaping 改变环境给出的监督；credit assignment 决定已有结果怎样归因到动作。添加中间分数后，如果训练器仍把它们求和为一个轨迹 scalar，再广播同一优势，局部 credit 依然不存在。反过来，Turn-PPO 不需要手工中间 reward，也能靠 critic/GAE 做局部归因。

当前 PRM-Lite 算不算真正的 PRM？

严格说不算 learned PRM，更准确是规则式 trajectory shaping。它先对 action history 中的重复、data chain、recovery 等事件打分，再取整条轨迹均值，与 outcome 按 outcome + 0.3 * process 融合；标准 GRPO 随后广播一个组优势。它能改善轨迹排序、提供可解释诊断，但没有过程标签训练、泛化校准和逐 Turn advantage 接线。

PRM 和 Turn-PPO critic 有什么区别？

Turn critic 估计当前 policy 下的 $V^\pi(s_t)$，目标来自 RL return/TD，随 policy 变化而变化；Agent PRM 通常评价状态—动作前缀的质量、promise 或 progress，可由 continuation outcome、可执行 action pair 和过程标签训练，也能独立用于 best-of-N。二者都可能长得像“成功概率”，但训练数据、条件变量、policy dependence 和使用路径不同，不能因为输出一个 scalar 就互换。

没有人工逐步标签，怎样训练 Agent PRM？

在每个真实 Turn 前缀采样多个 continuation，用规则 verifier 的成功率近似 promise；对工具参数、候选航班和恢复动作构造可执行 counterfactual pair；DB delta 与 policy compliance 提供硬标签；只有礼貌、解释和自然交互等不可执行维度才交给人工/独立 Judge。要保存 continuation policy 与 $K$，并用不确定性处理二值 Monte Carlo 的高方差。

PRM 应直接加到环境 reward 吗？

不应一开始就直接加。先验证它在 holdout 轨迹上能正确排序、定位最早错误，并用 best-of-N 证明对 verifier outcome 有正向作用；随后冻结版本、限制权重、逐 Turn 对齐进入 RL，终局 verifier 保持主锚点。直接相加会同时改变奖励目标、尺度和方差，一旦结果变好或变坏都很难归因。

User Simulator 为什么不能直接等同于 Judge？

Simulator 的任务是根据隐藏意图和历史产生下一个用户 observation；Judge 的任务是评估质量。二者目标不同。UserRL 原方法由规则 Gym 产生 reward，而不是让 simulator 自评。同一个模型兼任两者还可能偏好自己的表达风格、忽略工具真值，因此只能作为经校准的辅助信号。

为什么更强的 LLM 不一定是更好的用户模拟器？

更强模型往往更能猜懂 Agent、不经询问就补全信息、容忍含糊问题并推动任务成功，这会把环境变成 easy mode。用户模拟器的评价目标应是 goal consistency、披露策略、歧义/纠正/耐心等行为分布，以及用它训练的 policy 在 holdout simulator 与真人上的效用，而不是 simulator 自身语言能力或会话成功率。

如何防止 Actor 过拟合用户模拟器？

主消融固定 simulator 版本保证可归因；训练时使用有明确行为潜变量的 simulator pool；评测切换未见 prompt/model 与真人小样本；记录 slot 泄露、goal drift 和 stop 原因；检查 Actor 是否使用固定措辞诱导额外信息。训练 S1→评测 S1 很高但 S2/S3 骤降，就是 co-adaptation，不是算法泛化。

用户模拟器和 Judge 可以用同一个基座模型吗？

工程上能用，但不能把它当成独立证据。同一模型可能偏好自己的表达方式、共享相同知识盲点，并让“被自己模拟出来的会话被自己评高”形成相关偏差。若因资源必须复用，应使用不同 prompt/context、隐藏角色、独立规则 verifier，并通过异构模型与人工样本校准；算法主结论仍以可执行业务真值为准。

Simulator、PRM 和 Actor 都要迭代，为什么不端到端一起训？

因为三方同时变化会让环境转移、奖励函数和策略分布一起非平稳，训练 reward 无法解释。工程上按版本冻结：固定 simulator 收数据，训练并校准 PRM，冻结 PRM 更新 Actor，再用 holdout simulator/真人审计；新失败进入下一版本 replay。分阶段慢一些，但能定位是环境、监督还是优化器造成变化。

为什么不直接对 tool error 给负奖励？

工具错误有多类：格式错误、参数错误、业务拒绝、暂时不可用和能够暴露约束的可恢复错误。统一判负会鼓励模型少用工具或遇错放弃。应结合错误类型、后续恢复和终局状态；局部惩罚也不能覆盖最终 verifier。

Turn-PPO 的 critic 和 TRACE 的 reference probe 有什么本质区别？

critic 通过 RL 数据学习期望未来回报 $V^\pi(s)$，随 policy 和任务分布更新，可能有 bootstrapping bias。TRACE 的 reference 冻结，不预测回报，只测 gold target 在当前前缀下是否更可预测；它更像稳定的 task-progress proxy，偏差来自 target 与 reference 的语义能力。

为什么整轮 response ratio 可能不稳定？

整轮概率比是 token ratio 的乘积，即 log-ratio 的求和。响应越长，方差与极端值越容易积累，导致更多 clipping 或数值溢出风险。实现应在 log space 计算并监控长度分桶；任何几何平均或长度归一化都应作为明确消融，而非静默改写基线。

如何处理一组 rollout 全是 0 或全是 1？

先记录 effective group ratio，因为这是任务难度、探索与 group size 的诊断信号。可调整采样温度、课程难度、group size 或任务分层。不要随意加噪声奖励伪造组内差异；Turn-PPO 的 critic 或外部局部监督能缓解局部信号缺失，但终局组退化仍需单独监控。

如何防止 Agent 学会刷中间进展而不完成任务？

终局规则 verifier 始终作为锚点；local credit 只做辅助并有界；对重复检索、无效澄清和写操作回避做对抗测试；分别记录 outcome/local components；在 unseen 任务上检查是否真正完成，而不是只提高 Judge 或 prefix score。

SFT cold start 为什么仍然重要？

如果初始 policy 不会稳定地产生合法工具格式、遵守基本业务流程，绝大多数 rollout 都失败，组内 reward 退化，critic/TRACE 也只能在低质量前缀上学习。SFT 先建立可探索的行为支持，RL 再优化决策与恢复策略；但 SFT 数据与评测 task 必须防止污染。

如何证明方法不是只记住 task 模板？

按用户、约束组合和任务 ID 做严格 seen/unseen；检查训练数据污染；做参数扰动与 counterfactual tasks；再测 airline→retail 或新工具 schema 的迁移。除了 pass@1，还看策略 compliance、错误恢复和工具使用效率是否同时改善。

如果线上 rollout 是异步的，怎么控制 off-policy 偏差？

给每条轨迹记录 behavior policy version 和生成时 log-prob；计算 current/behavior ratio；限制最大 policy lag；拒绝或降权过期样本；监控 ratio、KL 与 clip fraction。KL reference 只负责策略锚定，不等于 behavior correction。

你会如何把三种方案排优先级？

先跑 outcome-only GRPO 作为预算等价基线；当前 τ-bench 有强终局 verifier，因此优先 Turn-PPO。只有能把业务中间状态可靠规则化时才做完整 UserRL；LLM Judge 先做离线诊断。TRACE 先验证 canonical target score 是否能正确排序关键 Turn 与错误恢复，再进入在线训练。

13 · Ready-to-use answer

两分钟面试回答模板

我理解的 Agentic RL，核心不是对长回答做 RLHF，而是把模型放进一个真实的序列决策闭环。模型每一轮基于完整历史决定要回复、澄清还是调用工具，环境返回用户或工具 observation，并可能改变数据库状态，所以更适合用 Turn-MDP 或 POMDP 来建模。

我会把五层分开。第一层是用户模拟器、工具和数据库，它们定义训练分布；第二层是规则 verifier，判断最终业务是否真的完成；第三层是 PRM/credit estimator，判断中间哪个动作提升了成功概率；第四层是 PPO/GRPO 的 ratio、clipping、KL 与 mask，把信号变成梯度；第五层是跨 simulator、跨任务和真人评测，验证没有共适应。标准 GRPO 是很好的 outcome baseline，但它把同一个组相对优势广播给整条轨迹，不能区分正确搜索、错误付款和后续恢复。

局部 credit 有四条代表路线。Turn-PPO 在 Turn 边界训练 critic，用终局 0/1 做 GAE；UserRL 要求 Gym 提供规则化逐 Turn 进展；TRACE 用冻结 reference 测量 canonical target 在不同前缀下是否更容易预测；learned Agent PRM 则可用 continuation 成功率和可执行 counterfactual pair 学习动作 promise/progress，并用于 rerank 或训练。PRM 不能只看 assistant 文本，还要看到工具结果和 DB delta；终局 verifier 始终是防 reward hacking 的锚点。当前仓库的 PRM-Lite 是规则式 trajectory shaping，不是完整 learned PRM，因为事件取均值后仍以终局 scalar 进入 GRPO；LATA 也只是位置权重，不能直接宣称精确 Turn credit。

用户模拟器同样决定上限。模型越强不一定越像真人：它可能过度理解、主动补全和配合，使任务变成 easy mode。主消融必须固定 simulator model/prompt/decoding；训练后再换 holdout simulator 和真人小样本做 cross-play，并监控 slot 泄露、goal drift、歧义、纠正和停止行为。对当前项目，我会先锁定环境与 verifier，复现 outcome-only GRPO；以严格 Turn-PPO 为主线，把 UserRL 与 TRACE 做独立监督消融；把 PRM-Lite 当弱监督基线，再构建可校准的 learned PRM，先做 best-of-N、再小权重接入 Turn credit。评价最终看 unseen verifier pass@1、错误恢复、政策合规、PRM 校准和 simulator cross-play gap，而不是只看训练 reward。

如果只剩 30 秒

Agentic RL 是在交互环境中优化长程决策。用户模拟器决定训练分布，规则 verifier 锁定最终业务真值，PRM/critic/TRACE 决定中间信用，PPO/GRPO 决定信号如何进入梯度。当前 τ-bench 应固定 simulator 做 outcome GRPO 基线，以 Turn-PPO 为主线；PRM-Lite 只算规则 shaping，learned PRM 要先用可执行标签校准并做 rerank，再接入 Turn credit；最终必须用 holdout simulator 和真人样本检验是否真正泛化。
