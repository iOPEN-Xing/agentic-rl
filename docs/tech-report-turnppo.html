Paper ↔ Code audit · Multi-turn agent RL

Turn-PPO：把一次完整交互当作强化学习的一步

多轮 Agent 的真正决策单位不是单个 token，而是一次“读环境—作响应—看结果”的完整 Turn。本页不仅解释论文，还逐项审计当前 codex/turn-level-reward 实现：哪些严格对应原式，哪些属于工程保护，以及它为何可以用于当前 τ-bench 航空数据。

阅读 ACL Anthology 原文 查看 arXiv HTML
01 · 背景

多轮任务是一个真正的序列决策问题

搜索、工具调用和环境反馈跨越多个 Turn；早期动作会改变后续可见状态，终局奖励却很稀疏。

02 · 矛盾

GRPO 把同一个结果归因给整条轨迹

组内归一化后的终局优势被广播给所有 token，既忽略不同 Turn 的贡献，也容易受多轨迹采样方差影响。

03 · 方法

Turn-MDP + 可学习 critic + Turn-Level GAE

状态是历史与当前查询，动作是整段模型响应；critic 在 Turn 边界估值，优势与 clipping 都按 Turn 计算。

04 · 效果

在 WebShop 与 Sokoban 上更稳、更有效

论文在不同模型和是否启用长推理的设置中，观察到 Turn-PPO 多数情况下优于 Token-PPO，并避免多种 GRPO 崩溃。

阅读路径：先理解 GRPO 的归因错位 → 拆 Turn-PPO 的状态、critic、GAE 与 actor 目标 → 用“论文符号—张量—函数”核对当前代码 → 沿真实 task_id=0 走完数据、工具、reward、张量和 optimizer step → 最后用业务与算法双层指标判断是否有效。

01 · Problem

问题不只是“奖励稀疏”，而是决策粒度错了

单轮回答里，把 token 当作 MDP step 尚且自然；但多轮交互会在两次模型响应之间突然插入整段用户消息或工具输出。Token-MDP 因此混合了两种完全不同的状态转移：追加一个 token，以及注入一整块外部信息。

这会造成两类噪声。首先，GRPO 的组相对优势依赖同一问题的多条 rollout，环境随机性会放大估计方差。其次，同一轨迹中的所有 Turn 被赋予近似相同的优势：一次正确搜索与最后一次错误提交可能一起被惩罚；一次无效尝试也可能因为终局成功而被奖励。

多次采样轨迹同一请求与环境交互多次，得到不同终局奖励。
组内标准化奖励减均值、除标准差，形成每条轨迹一个优势值。
广播到全部 Turn关键动作、冗余动作与错误动作共享同一方向的训练信号。

最小例子：订票 Agent 前三步正确澄清日期、搜索航班并确认舱位，最后却用了不存在的支付方式。Outcome-only GRPO 只能说“这条轨迹失败”，无法告诉模型前三步值得保留、最后一步才应被修正。

三种方案到底差在哪里

GRPO

不训练 critic。用组内终局奖励估计整条轨迹的优势，成本较低，但在长轨迹里信用分配很粗。

Token-PPO

训练 token-level critic。每个 token 都是一步；外部反馈造成不连续的状态转移，critic 更难学准。

Turn-PPO

训练 turn-level critic。一次完整响应是一项动作，状态始终位于真实交互边界，优势更贴近任务结构。

02 · Method

先看全局图：改变的是 MDP 切分方式

下面这张原论文 Figure 1 把 GRPO、Token-PPO 与 Turn-PPO 放在同一条多轮轨迹上。先看 value 和 advantage 出现在哪里，再看公式，会比从 GAE 推导入手更容易理解。

方法拆成五步

1. 切 Turn以用户输入或工具观察到达、模型响应结束为边界。
2. 定义状态$s_n$ = 完整历史 + 当前环境查询 $Q_n$。
3. 定义动作$a_n$ = 模型在本 Turn 生成的完整响应 $R_n$。
4. 边界估值预训练 LLM 加 value head，预测每个 Turn 状态的未来回报。
5. GAE 与更新按 Turn 递推优势，并在整段响应级别计算 ratio、clipping 与损失。
结果同一响应内信号一致，不同响应之间信用可分。

四条公式把 critic 与 actor 串成闭环

$$\delta_n = r_n + \gamma V(s_{n+1}) - V(s_n),\qquad A_n = \delta_n + \gamma\lambda A_{n+1}$$

Turn-Level GAE：第 $n$ 个 Turn 的优势，由“本轮奖励 + 下一 Turn 状态价值 − 当前 Turn 状态价值”开始，再把未来 TD 误差按 $\gamma\lambda$ 衰减传回。当前航空实现采用稀疏终局奖励，即 $r_1=\cdots=r_{N-1}=0,\ r_N=R_{\mathrm{terminal}}$。

$$\rho_n(\theta)=\frac{\pi_\theta(a_n\mid s_n)}{\pi_{\theta_{\mathrm{old}}}(a_n\mid s_n)} =\prod_{h=1}^{|a_n|} \frac{\pi_\theta(a_{n,h}\mid s_{n,h})}{\pi_{\theta_{\mathrm{old}}}(a_{n,h}\mid s_{n,h})}$$

整轮概率比：生产代码不直接连乘概率，而是先求 $\sum_h(\log\pi_\theta-\log\pi_{\mathrm{old}})$ 再取指数；数学上等价，数值上更稳。用户消息、工具观察和 padding 的 turn_id=0，不会进入该乘积。

$$\mathcal L_{\mathrm{actor}} =\frac{1}{B}\sum_{i=1}^{B}\frac{1}{|a^i|} \sum_{n=1}^{N_i} \max\!\left[-\rho_{i,n}A_{i,n}, -\operatorname{clip}(\rho_{i,n},1-\epsilon,1+\epsilon)A_{i,n}\right]$$

Table 1 的关键归一化：$|a^i|$ 是第 $i$ 条轨迹全部 assistant action token 的总数，不是 Turn 数；先得到每条轨迹的目标，再对轨迹取均值。这与“把所有 batch token 做一次全局平均”不同。

$$\mathcal L_{\mathrm{critic}} =\frac{1}{B}\sum_{i=1}^{B}\frac{1}{N_i} \sum_{n=1}^{N_i}\frac{1}{2}\left(V_\phi(s_{i,n})-\widehat R_{i,n}\right)^2$$

边界 critic：每条轨迹先对 $N_i$ 个 Turn 状态平均，因此长对话不会仅因 Turn 更多而压过短对话。当前代码再叠加标准 PPO 的 value clipping；这是优化保护，不改变 critic 只在 Turn 边界学习的定义。

两个容易误解的点：第一，严格 Turn-PPO 不是给每个 Turn 人工编一个“正确性奖励”，而是让 turn-level critic 从终局回报的统计规律中学习价值；所以它改善的是信用估计，不会凭空获得步骤级真值。第二，论文在单轮 Turn-MDP/GRPO 讨论过响应概率比的几何平均及其与 GSPO 的关系，但严格的多轮 Turn-PPO 基线使用上面的整轮乘积。几何平均可以做稳定性消融，不能写成当前实现已经采用的公式。

03 · Paper ↔ implementation

当前代码不是“近似像 Turn-PPO”，而是按严格基线闭环

审计结论是：当前分支的主训练链路在算法定义上准确。它没有把旧的 heuristic turn reward、potential shaping 或额外 rollout importance sampling 混入 Turn-PPO，而是从 rollout 产出 Turn 身份，经过 Turn-GAE 和边界 critic，最后进入整轮 actor 目标。真正需要警惕的不是公式写错，而是长响应概率比的方差与 critic 是否从二值终局反馈中学到可泛化的状态价值。

论文对象当前张量 / 代码入口双向审计结论
状态 $s_n$：完整历史 + 当前环境输入 dp_critic.py 的因果位移；第一个 assistant token 位置保存响应前状态的 value 准确。工具观察保留在完整上下文中，但不进入 actor mask。
动作 $a_n$：一整段 assistant response assistant_turn_spans → turn_ids；正整数标识响应，环境与 padding 为 0 准确且 fail-loud。乱序、跳号、覆盖环境 token、同一 Turn 被拆开都会报错。
稀疏奖励 $r_n$ compute_turn_gae_advantage_return 把整轨迹 reward sum 放到最后一个 Turn 适配当前数据。τ-bench 提供可验证终局结果；旧 shaping 默认关闭。
Turn-Level GAE turn_gae：仅在 Turn 起点递推，再把 $A_n$ 广播给本 Turn token 准确。优势归一化只发生在 Turn 起点，而非重复广播后的 token 上。
critic 的 $1/N_i$ 轨迹内平均 turn_value_mask[start] = 1 / N_i 准确。每条非空轨迹的 critic mask 权重之和为 1。
整轮 ratio 与单次 clipping compute_policy_loss_turn_ppo：先 sum log-ratio，再 exp、clip 准确。不是 token-by-token clipping，也没有追加第二套 rollout IS。
长响应数值保护 turn_log_ratio 截断到 $[-20,20]$，并记录 saturation fraction 合理但需监控。这是工程保护；频繁触发意味着策略漂移或响应过长，不能把它当成无害常数。

从一个 token 位置读出“响应前状态”的 value

论文说 $V(s_n)$ 位于当前查询或环境输出的末尾；veRL 的 value 张量与 response token 对齐且向前错一位。因此，代码在“第一个 assistant token 的槽位”读取的，实际是看到该 token 之前全部上下文后的 value。两种说法在因果语言模型中是同一个状态，不应再额外维护一份 state_end_index。

可运行核心：Turn-GAE + response-product PPO 仅依赖 Python 标准库；复制后即可运行。 
from math import exp

def turn_gae(rewards, values, gamma=0.99, lam=0.9):
    """rewards=[0, ..., terminal_reward]；values[n]=V(s_n)。"""
    advantages = [0.0] * len(rewards)
    next_advantage = 0.0
    for n in range(len(rewards) - 1, -1, -1):
        next_value = values[n + 1] if n + 1 < len(values) else 0.0
        delta = rewards[n] + gamma * next_value - values[n]
        next_advantage = delta + gamma * lam * next_advantage
        advantages[n] = next_advantage
    returns = [a + v for a, v in zip(advantages, values)]
    return advantages, returns

def one_turn_loss(old_logp, new_logp, advantage, token_denominator,
                  epsilon=0.2):
    """整轮先乘 ratio（log 域求和），然后只 clip 一次。"""
    log_ratio = sum(new - old for old, new in zip(old_logp, new_logp))
    ratio = exp(max(-20.0, min(20.0, log_ratio)))
    clipped = max(1.0 - epsilon, min(1.0 + epsilon, ratio))
    surrogate_loss = max(-advantage * ratio, -advantage * clipped)
    return surrogate_loss / token_denominator

advantages, returns = turn_gae([0.0, 1.0], [0.0, 0.0],
                               gamma=0.5, lam=1.0)
assert advantages == [0.5, 1.0]

# exp(0.2 + 0.2) 超过 1.2：整轮目标被 clip 到 -1.2，
# 再按本轨迹两个 assistant token 归一化，得到 -0.6。
loss = one_turn_loss([0.0, 0.0], [0.2, 0.2], 1.0, 2)
assert abs(loss - (-0.6)) < 1e-12

真实样本解剖：从 task_id=0 到一次 Turn-PPO 更新

下面不是虚构订票脚本，而是当前仓库中可追溯的 τ-bench 航空任务。task_id=0 位于训练 seen split；它要求预订 5 月 20 日纽约到西雅图的单程经济舱，11 点后出发、优先直飞否则一次中转、最低价、3 件行李、不买保险，并优先使用较大代金券支付。

训练索引

业务正确答案

可追溯成功轨迹

RL 中如何使用

用具体数字看：终局 1 如何变成 6 个不同的 Turn 信号

历史 JSONL 没有保存训练时 critic 的 value，因此下面的 $V(s_n)$ 是教学性假设，不是实验观测。假设 critic 随业务事实逐渐完整而给出 $[0.10,0.18,0.32,0.48,0.72,0.90]$，使用当前配置 $\gamma=0.99,\lambda=0.9$，显式 reward 为 $[0,0,0,0,0,1]$，则未 whitening 的结果如下。

1 · 查直飞0.100000.07820.65190.7519
2 · 查中转0.180000.13680.64390.8239
3 · 用户确认0.320000.15520.56910.8891
4 · 查账户0.480000.23280.46450.9445

这张表揭示了业务落地时最重要的语义：Turn-PPO 奖励的不是“离终点越近越多”。Turn 6 虽然接到终局 1，但 critic 已预测 0.9，所以 surprise 只有 0.1；前面的搜索与确认通过提高下一状态价值，也能获得较大的正 TD 信号。生产代码会在 batch 的所有 Turn 起点上 whitening，所以上表绝对值不会原样进入 actor，但状态间的相对信息来自这条递推。

工具错误不是人工负标签：同一任务的另一个真实历史 attempt 曾把 255 美元误付成 305 美元，工具返回 error 后，模型下一 Turn 修正为 250+5 并最终成功。严格 Turn-PPO 不应看到 error 就硬加负 reward；它让 error observation 改变下一状态价值，并根据最终是否恢复来学习。这样既惩罚不可恢复的错误，也保留“发现并修正错误”的业务能力。

一次 optimizer step 实际优化了什么

  1. critic：只在 6 个 Turn 起点回归上表的 $\widehat R_n$；每个起点 mask 权重为 $1/6$，整条轨迹总权重为 1。
  2. advantage：每个 $A_n$ 在本 Turn 的全部 assistant token 上广播；搜索工具参数、解释文字和最终确认属于各自完整动作。
  3. actor ratio：分别把 Turn 1 到 Turn 6 的 token log-ratio 求和、取指数并各 clip 一次；工具 JSON 和用户回复完全不进入 ratio。
  4. 轨迹归一化：6 个 Turn surrogate 求和后除以本轨迹 assistant token 总数，再与 batch 中其他 31 条轨迹等权平均。
  5. 业务效果：如果类似状态上的正确搜索、约束确认和支付组合持续通向成功，它们的概率会上升；一次偶然成功不会自动把每个步骤认定为正确。

从算法健康到业务上线：指标必须分三层

层级应回答的问题当前可直接观测建议补齐
业务结果 数据库最终状态是否精确满足用户约束？是否能泛化到未见任务？ binary outcome、seen/unseen split、val success。 按 booking / change / cancel、约束数量和任务长度分桶的成功率及置信区间。
业务安全 是否产生错误工具调用、无效写操作或过早转人工？ total_errors、total_tool_calls、error rate；环境保留 transfer 状态。 写工具错误率、不可恢复数据库变更率、转人工率及失败原因 taxonomy。
业务效率 成功是否以更少交互和更低推理成本完成？ assistant/user Turn 数、tool calls、reasoning_tokens_per_turn。 success-conditioned Turn/token 成本，避免模型靠拉长对话换成功率。
critic 可信度 value 真在识别业务进度，还是只记住 Turn index 和工具名？ critic/vf_loss、critic/vf_clipfrac、value mean。 held-out explained variance、value calibration，以及相同前缀的反事实后续对比。
actor 稳定性 整轮 product ratio 是否仍在可学习区间？ Turn clip fraction、KL、Turns per sequence、log-ratio saturation fraction。 按 response 长度和工具类型分桶的 clip/saturation，定位长 reasoning 的方差来源。

业务验收顺序：先要求 unseen success 在多随机种子下改善；再确认工具错误率、错误写操作和转人工没有恶化；最后比较 success-conditioned Turn/token 成本。只有三层同时成立，才能说 Turn-PPO 把算法增益转成了真实业务增益，而不是只把训练 reward 做高。

05 · Engineering mapping

适配结论：当前 τ-bench 数据与框架都能承载 Turn-PPO

这一节是对当前航空项目的工程审计，不是 Turn-PPO 论文中的实验。结论不是“换回另一个框架才能做”：当前 veRL agent loop 已经具备完整交互历史、assistant span、工具观察和可验证终局奖励，足以构造 Turn-MDP；需要新增的 critic 与专用 loss 也已接入。真正的不确定性是统计效率，而不是数据结构不兼容。

为什么这份数据可用：parquet 中的 prompt 只是任务入口；环境 reset() 返回的初始观察会在第一次生成前追加为 user message，所以 $s_1$ 不是“只有 system prompt”。之后每次工具结果也进入完整上下文。若工具 metadata 标记 done，发起该终局工具调用的 assistant response 就是最后一个动作，不会再凭空生成一个没有环境后继的 Turn。

Turn状态 $s_n$动作 $a_n$critic 应估计的含义
澄清需求用户初始请求追问日期、人数或舱位获得完整可执行约束后，未来成功预订的期望回报
搜索航班历史 + 已澄清约束调用搜索工具并组织参数正确候选航班进入上下文后，后续完成任务的可能性
确认选择历史 + 搜索结果向用户呈现候选并请求确认用户选择是否把轨迹推进到可提交状态
执行预订历史 + 用户确认调用预订工具并返回结果终局成功、政策合规与工具执行结果

初始 user request 与 system prompt 一起位于 prompts；后续用户消息和工具观察进入 responses 时，其 turn_id 与 response_mask 都设为 0。actor 只训练模型生成的 response token，但 critic 的因果输入始终保留完整历史。工具调用参数与同一 assistant response 中的自然语言属于一个动作，共享一个 $A_n$。这正好匹配 τ-bench 中“生成工具调用 → 环境执行 → 返回观察”的自然边界。

公平预算：GRPO 与 Turn-PPO 都消费 32 条 rollout 组大小不同，但采样轨迹总数对齐，避免把更多环境交互误当成算法增益。
  • vanilla GRPO：train_batch_size=4、rollout.n=8，共 32 条轨迹；同一 prompt 的 8 条 rollout 用于组相对优势。
  • Turn-PPO：train_batch_size=32、rollout.n=1，同样是 32 条轨迹；价值基线来自 critic，不要求同 prompt 组采样。
  • 仍需单独报告：critic 的参数、优化器状态、forward/backward 与显存是 Turn-PPO 的额外成本，不能用“rollout 相等”掩盖。
验证切片：用失败预订检查优势是否分化 它是 critic 信用分配的诊断，不是预设“正确步骤必为正优势”。
  • 对照组：原始 GRPO 给整条轨迹同一个轨迹级优势，无法区分失败发生前后的响应。
  • Turn-PPO：按失败前阶段、工具类型和错误类型分桶，检查 $V(s_n)$、TD error 与 $A_n$ 是否呈现稳定而可解释的差异；单条轨迹上的正负不等价于步骤真值。
  • 必要诊断：记录 value loss、explained variance、每 Turn advantage 分布、episode success、整轮 clip fraction，以及 turn_ppo_log_ratio_saturation_fraction。
  • 反事实检查：对相同前缀比较不同后续动作/结果，才能更有力地判断 critic 是学到进度，还是只记住位置、长度或工具名称。

06 · Evidence

实验真正证明了什么

论文的证据重点不是一个孤立的最高分，而是：在不同任务、不同骨干模型、是否启用长推理的多种设置中，Turn 粒度让 PPO 的优势估计更可靠；反过来，GRPO 在多轮长推理中会出现系统性训练崩溃。

2互补环境：WebShop 测交互式购物，Sokoban 测长程规划与不可逆动作。
3 类核心比较：GRPO、Token-PPO、Turn-PPO，统一放在多轮 MDP 框架下。
≈ 同 PPO 成本论文指出 Turn-PPO 与 Token-PPO 的 actor/critic 前后向形式相近；这不表示它与无 critic 的 GRPO 成本相同。
  • GRPO 失败诊断：去除标准差归一化、调整 KL 或增加 batch diversity 都不能稳定消除崩溃，说明问题不只是某个超参数。
  • PPO 对比：可学习 critic 让 PPO 比采样式组相对优势更稳定；Turn-level critic 又通常比 Token-level critic 更准确。
  • 适用范围：论文只研究文本环境 WebShop 与 Sokoban；对真实工具 API、非平稳用户和更长航空任务的泛化仍需单独验证。
  • 当前代码证据：源码审计和 CPU 级数学测试只能证明“实现的是预期公式”，不能证明它在航空任务上一定优于 GRPO；最终结论仍需受控训练实验。

07 · Critical reading

最终判断：方案一适用当前数据，也适合当前框架

为什么可以作为主线

τ-bench 有自然 Turn 边界、完整工具历史和可验证终局奖励；当前 veRL 改造已把 rollout、critic、GAE 与 actor loss 接通，无需换回另一套训练框架。

最大的理论风险

二值终局反馈没有步骤级真值，critic 只能从跨轨迹统计规律学习；若失败样本占比过高或状态覆盖不足，Turn advantage 可能只是带偏差的 value 残差。

最大的实现风险

长 reasoning response 会让整轮概率比的方差随 token 数累积。若 clipping 或 log-ratio saturation 长期偏高，应先处理更新幅度，而不是静默改成另一种算法。

什么结果才算“这套方案在当前数据上工作”

路线建议：保留当前 veRL 实现，按原技术报告的严格 Turn-PPO 定义作为方案一主线，不需要因为数据集而退回“人工 turn reward shaping”。首轮实验优先验证 critic 的 held-out 解释力和整轮 ratio 的稳定性。只有当 log-ratio 饱和成为结构性问题时，再把几何平均/长度归一化 ratio 作为清晰命名的算法消融；只有当 critic 明显学不动时，再比较 TRACE 等 critic-free 方案。
